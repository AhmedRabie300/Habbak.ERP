# تحسينات وتصحيحات على مستوى النظام — دفعة 2
## مبدأ عام موحّد لكل القوائم المنسدلة (Dropdown Lists) في النظام

> يكمّل هذا الملف `00-System-Wide-Corrections-01.md`. المبدأ هنا **ينطبق على كل قائمة منسدلة في كل شاشة من كل موديول** بدون استثناء — بما فيها الشاشات المُنجَزة بالفعل في `01-Module-Accounting.md` و`02-Module-Inventory-Manufacturing.md` (تم تطبيقه بأثر رجعي جزئيًا كما هو موضّح في قسم 4).

---

## 1. المبدأ العام

كل قائمة منسدلة (`Dropdown` / `Select`) في أي شاشة بالنظام، بدون استثناء، لازم تلتزم بثلاث قواعد معًا:

1. **مصدر بياناتها كيان له شاشة إدخال/إدارة مخصصة**، وبنيته الأساسية دايمًا: **كود (`Code`) + اسم عربي (`NameAr`) + اسم إنجليزي (`NameEn`) + حالة تفعيل (`IsActive`)** — حتى لو الكيان عنده حقول إضافية تانية.
2. **العرض في القائمة المنسدلة يتبع لغة واجهة المستخدم الحالية تلقائيًا** — `NameAr` لو اللغة عربي، `NameEn` لو إنجليزي (`00-Project-Overview.md` قسم 4) — بدون أي منطق إضافي من الشاشة المستخدِمة للقائمة.
3. **كل قائمة منسدلة قابلة للبحث (Searchable) إلزاميًا** — لا يوجد أي `Dropdown` في النظام بشكل قائمة تمرير عادية بدون خانة بحث، بغض النظر عن عدد العناصر فيها.

## 2. التطبيق التقني على الباك إند

### 2.1 الواجهة الموحّدة `ILookupEntity`
```csharp
public interface ILookupEntity
{
    long Id { get; set; }
    string Code { get; set; }
    string NameAr { get; set; }
    string NameEn { get; set; }
    bool IsActive { get; set; }
}
```
**أي كيان في أي موديول يُستخدم كمصدر بيانات لقائمة منسدلة لازم ينفّذ الواجهة دي كحد أدنى** — سواء كيان مخصص بحقول إضافية كتيرة (`Warehouse`, `Item`, `Account`) أو كيان بسيط (`LookupValue`, قسم 2.2).

### 2.2 قاعدة عامة على مستوى النظام بالكامل: كل شاشة Lookup لها جدول مستقل
**لا يوجد جدول مرجعي عام مشترك (`LookupType`/`LookupValue` أو أي نظام مماثل) في هذا النظام.** تم تجربة هذا النمط وإلغاؤه صراحةً — كل تصنيف/قائمة مرجعية في أي موديول، **حتى لو بسيطة جدًا وبلا حقول إضافية** (مثال: طريقة تحصيل، سبب رفض، نوع ملاحظة)، لازم يكون ليها:
- **كيان (Entity) وجدول مستقل خاص بيها** في الـ Domain، بنفس اسمها (مثال: `PaymentMethod`, `RejectionReason`).
- **شاشة إدارة (List/Edit) مستقلة خاصة بيها** — مش لوحة عامة واحدة لكل الأنواع.
- الحد الأدنى لشكل الكيان يفضل زي ما هو: `Code`/`NameAr`/`NameEn`/`IsActive` (تنفيذ `ILookupEntity`، قسم 2.1) — بالإضافة لأي حقول تانية خاصة بيها لو احتاجت.

السبب: كل قائمة مرجعية بتكبر مع الوقت وبتحتاج حقول/علاقات خاصة بيها (ترتيب عرض، ربط بموديول تاني، قواعد عمل مختلفة) ما بتنفعش تتقاسم جدول عام مع تصنيفات تانية مالهاش نفس الاحتياجات — فالأسهل إدارةً وصيانةً إن كل واحدة تاخد جدولها من الأول، حتى لو الشكل الأولي بسيط.

### 2.3 API موحّد
كل كيان مرجعي (Lookup) — بسيط كان أو معقد — بيتبع نفس عقد الـ `GetList` القياسي (`00-Frontend-Specs.md` قسم 6)، مع ضمان وجود الحقول الأربعة `Code`/`NameAr`/`NameEn`/`IsActive` على الأقل في الاستجابة. لا يوجد `endpoint` عام مشترك لكل أنواع القوائم — كل كيان له الـ Controller الخاص بيه زي أي كيان تاني في النظام.

## 3. التطبيق التقني على الفرونت إند

### 3.1 مكوّن `Select` — تحديث إلزامي
مكوّن `Select` الموجود بالفعل في `@habbak/ui-kit` (`00-Frontend-Specs.md` قسم 3.3) يُحدَّث ليصبح:
- **قابل للبحث دايمًا (Combobox/Typeahead)** — لا يوجد وضع "قائمة عادية غير قابلة للبحث" في النظام كله، ولا يوجد Prop لتعطيل الخاصية دي.
- **يحل اسم العرض تلقائيًا** من `nameAr`/`nameEn` حسب لغة الواجهة الحالية (Zustand، `00-Frontend-Specs.md` قسم 2) — الشاشة المستخدِمة للمكوّن مش محتاجة تعمل المنطق ده بنفسها.

### 3.2 كل كيان مرجعي له Hook خاص بيه
بما إنه مفيش جدول عام مشترك (قسم 2.2)، مفيش Hook عام واحد لكل القوائم — كل كيان مرجعي له ملف `api.ts` وHook خاص بيه زي أي كيان تاني في النظام، مثال:
```tsx
const { data: paymentMethods } = usePaymentMethodsList();
const { data: warehouses } = useWarehousesList();
```
كل Hook من دول بيرجّع بيانات بالشكل القياسي `{ id, code, nameAr, nameEn, isActive }` (زائد أي حقول خاصة بالكيان)، جاهزة تتغذّى مباشرة لمكوّن `SearchableSelect`/`SearchableMultiSelect` (`ui-kit`).

### 3.3 مثال الاستخدام
```tsx
<SearchableSelect
  value={selectedWarehouseId}
  onChange={setSelectedWarehouseId}
  options={warehouses.map((w) => ({ value: w.id, label: currentLanguage === 'ar' ? w.nameAr : w.nameEn }))}
/>
```
لاحظي عدم وجود أي Prop لتعطيل البحث — القابلية للبحث سلوك افتراضي غير قابل للإلغاء (قسم 1، بند 3).

## 4. الأثر بأثر رجعي على الملفات المُنجَزة

### 4.1 `01-Module-Accounting.md` — تم التصحيح فعليًا
تم اكتشاف عدم توافق أثناء كتابة هذا الملف وتصحيحه فورًا في `01-Module-Accounting.md`:
- `CostCenterDimension`: كان بيحمل حقل `Name` واحد فقط — **تم تصحيحه لـ `NameAr`/`NameEn`**.
- `CostCenterDimensionValue`: كان بيحمل حقل `Name` واحد فقط **وبدون `IsActive` أصلًا** — **تم تصحيحه لـ `NameAr`/`NameEn` + إضافة `IsActive`**.
- القاعدة 29 اتحدّثت لتشاور على `NameAr`/`NameEn` بدل `Name`.

### 4.2 `02-Module-Inventory-Manufacturing.md` — تم الفحص، متوافق بالفعل
كل الكيانات المرجعية في هذا الملف (`UnitOfMeasure`, `Warehouse`, `Item`, وغيرهم) كانت ملتزمة بالفعل بشكل `Code`/`NameAr`/`NameEn`/`IsActive` — **لا تعديل مطلوب**.

### 4.3 قاعدة عامة للموديولات القادمة
أي كيان مرجعي جديد في `03-Module-Purchasing.md` وما بعده **يُكتب مباشرة بالشكل الصحيح من البداية** (`Code`/`NameAr`/`NameEn`/`IsActive`) — لا حاجة لمراجعة تصحيحية لاحقة إن شاء الله، بما إن المبدأ موثّق الآن كمرجع ثابت في هذا الملف.
