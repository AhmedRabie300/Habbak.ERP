# الواجهة الأمامية (Frontend) — نظام الحبّاك
## مواصفات ثابتة على مستوى النظام

> هذا الملف مكمّل لـ `00-Project-Overview.md` ومرجع إلزامي لأي شاشة Frontend في أي موديول.

## 1. الهدف من هذا الملف

- تثبيت **الـ Stack الأمامي** ومكتباته المصاحبة.
- تثبيت **نظام تصميم موحّد (Design System)** وكنترول شبكة عرض واحد (Standard Data Grid).
- تثبيت **نمط الشاشة القياسي**: List ← Search ← GetList API ← Edit.
- توثيق **عقد الـ API** بما فيه شكل الأخطاء، الصلاحيات، التوجيه المحمي، تعدد اللغات، التحديثات اللحظية، **والعمل بدون إنترنت**.
- تثبيت سياسات **الأداء، إمكانية الوصول، والاختبار**.

## 2. الـ Stack الأمامي (Frontend Stack)

| العنصر | الاختيار | ملاحظات |
|---|---|---|
| المكتبة الأساسية | **React** — أحدث إصدار **مستقر** وقت البدء الفعلي | — |
| اللغة | **TypeScript** | إلزامي |
| أداة البناء (Build Tool) | **Vite** | متسقة مع معيار متغيرات البيئة في قسم 11 |
| التوجيه (Routing) | **React Router** | كل شاشة لها Route ثابت (قسم 5)، محمي افتراضيًا (قسم 9) |
| حالة السيرفر (Server State) | **React Query (TanStack Query)** | إلزامي بدل `useEffect` + `fetch` يدوي |
| حالة الواجهة العامة (Global UI State) | **Zustand** | مسؤول حصريًا عن: المستخدم الحالي، الشركة والفرع النشطين، لغة الواجهة. لا يُستخدم لحالة خاصة بشاشة واحدة |
| التخزين المحلي للعمل بدون إنترنت | **IndexedDB** (عبر **Dexie.js**) | تفاصيل كاملة في قسم 15 — **وليس** `localStorage` |
| النماذج والتحقق | **React Hook Form** + **Zod** | نفس قواعد الـ Backend (FluentValidation) قدر الإمكان |
| نداءات HTTP | **Axios** مع Instance مركزي واحد | معالجة الأخطاء الموحّدة (قسم 12) |
| تقسيم الكود | **`React.lazy` + `Suspense`** على مستوى كل موديول | تفاصيل في قسم 13 |
| التحديثات اللحظية | **SignalR** | تفاصيل في قسم 14 |
| الترجمة (i18n) | **react-i18next** | تفاصيل في قسم 10 |
| مكتبة مكوّنات أساسية (Headless) | **Radix UI** (أو مكافئها) كأساس، وفوقها مكتبة التصميم الخاصة (قسم 3) | ممنوع استخدام أي UI Kit جاهز التصميم مباشرة |
| الرسوم البيانية | **Recharts** أو **Chart.js** (قرار معلّق) | للوحة التحكم والتقارير |

> **ملاحظة**: التكامل مع الأجهزة الفعلية (موازين، طابعات، ماكينات دفع) **لا يتم مباشرة من الفرونت** (لا `WebUSB`/`WebSerial`) — يتم عبر تطبيق **Local Agent** محلي موثّق في `00-Project-Overview.md` (قسم 5.4). الفرونت بيتواصل مع الـ Local Agent ده عبر API محلي بس.

## 3. نظام التصميم الموحّد (Design System)

### 3.1 المبدأ الأساسي
**ممنوع** أي شاشة تكتب Styling خاص بيها لعنصر أساسي. كل عنصر أساسي له نسخة واحدة قياسية في مكتبة داخلية مشتركة (`@habbak/ui-kit`).

### 3.2 Design Tokens
الألوان (هوية الحبّاك: كحلي وذهبي)، الطباعة (لكل لغة)، مقياس المسافات الثابت، الحواف والظلال.

### 3.3 مكتبة المكوّنات (Component Library)
`Button`, `Input`, `Select`, `DatePicker`, `Checkbox`, `Toggle`, `Modal`, `Toast`, `Badge`, `Tabs`, `Skeleton`, `DataGrid` (قسم 4)، `AttachmentsPanel` (لوحة المرفقات القياسية داخل أي شاشة Edit)، و`ExportButton` (تصدير Excel/PDF/CSV/طباعة من أي `DataGrid` أو تقرير) — تفاصيل سياسة الاثنين الكاملة في `00-Project-Overview.md` (قسم 8.5).

قاعدتان ثابتتان (تفاصيل في قسم 12): **`Skeleton`** هو النمط الافتراضي الوحيد لحالة التحميل، و**`Toast`** هو النمط الافتراضي الوحيد لرسائل الحالة العابرة.

## 4. الكنترول الأساسي: شبكة العرض الموحّدة (Standard Data Grid)

### 4.1 التعريف
```tsx
<DataGrid
  entityKey="journal-entries"
  columns={journalEntryColumns}
  fetchEndpoint="/api/v1/accounting/journal-entries"
  searchable={true}
  onRowClick={(row) => navigateToEdit(row.id)}
  canEdit={(row) => row.status === 'Draft'}
  defaultPageSize={25}
/>
```

### 4.2 تعريف الأعمدة
`key`, `label` (عربي/إنجليزي)، `type` (`text`/`number`/`date`/`currency`/`badge`/`custom`)، `width` اختياري.

### 4.3 السلوك القياسي الإلزامي
1. عند الفتح لأول مرة: استدعاء GetList فورًا بمعايير افتراضية.
2. أثناء الانتظار: صفوف `Skeleton`.
3. البحث: Server-side دايمًا.
4. الضغط على صف: `canEdit(row)` + صلاحية → Edit، وإلا → عرض فقط.
5. الـ Pagination والترتيب: من السيرفر دايمًا.

## 5. نمط الشاشة القياسي (List → Search → Edit)

```
/accounting/journal-entries              → List
/accounting/journal-entries/:id          → Edit/View
/accounting/journal-entries/new          → Create (لو مسموح)
```

الانتقال دايمًا عبر الـ Router، مش Modal فوق نفس الصفحة.

## 6. عقد الـ GetList API

**الطلب:** `GET /api/v1/{module}/{entity}?search=&page=1&pageSize=25&sortBy=&sortDir=asc`

**الاستجابة:** `{ "items": [ ], "totalCount": 348, "page": 1, "pageSize": 25 }`

الفلترة حسب `CompanyId`/`BranchId` تتم تلقائيًا في الـ Backend.

## 7. نمط شاشة التعديل (Edit Screen Pattern)

1. `GET .../{id}` لجلب البيانات كاملة (بما فيها `RowVersion`).
2. `PUT .../{id}` للحفظ مع `RowVersion` — `409 Conflict` يعرض رسالة موحّدة.
3. شريط حالة الموافقة أعلى الفورم لو مرتبطة بسلسلة (قسم 18).
4. أزرار موحّدة: "حفظ" / "إلغاء" / أزرار حالة المستند في شريط منفصل.

---

## 8. العرض حسب الصلاحيات (Permission-Based Rendering)

- كل عنصر تفاعلي يُعرض/يُخفى بناءً على صلاحيات المستخدم الفعلية من الـ Backend، عبر Hook مركزي: `usePermission(entityKey, action)`.
- **قاعدة أمان أساسية**: إخفاء عنصر في الفرونت تحسين لتجربة المستخدم فقط — الـ Backend لازم يتحقق بشكل مستقل دايمًا.
- الحقول الحساسة تُستبعد من استجابة الـ API نفسها، مش تُستقبل وتُخفى.

---

## 9. التوجيه المحمي (Protected Routes)

- كل Route محمي افتراضيًا عبر `<ProtectedRoute>` (يتطلب جلسة صالحة — `00-Project-Overview.md` قسم 7).
- صلاحيات إضافية: `<ProtectedRoute requiredPermission="settings.manage">`.
- بدون صلاحية كافية → صفحة "غير مصرَّح" (403)، وليس صفحة تسجيل الدخول.

## 15. العمل بدون إنترنت والمزامنة (Offline Mode & Sync)

### 15.1 النطاق
وضع العمل بدون إنترنت مخصص لعمليات **الإنشاء المتسلسل في نقاط البيع تحديدًا** (فاتورة بيع جديدة، فتح/إغلاق وردية) — وليس لكل شاشات النظام. شاشات الإدارة والتقارير تتطلب اتصال دايمًا.

### 15.2 التخزين المحلي
- **IndexedDB** (عبر **Dexie.js**) هو مخزن البيانات المحلي — **وليس** `localStorage` (محدود الحجم وغير مناسب لبيانات منظّمة).
- جدولان محليان منفصلان حسب اتجاه البيانات (تفاصيل الثاني في قسم 15.6):
  - **`OutboxTransactions`** — بيانات صاعدة من الجهاز للسيرفر: العمليات اللي اتعملت Offline ولسه محتاجة تتبعت.
  - **`ReferenceDataCache`** — بيانات نازلة من السيرفر للجهاز: الأصناف والأسعار والخصومات، تُستخدم للقراءة وقت البيع Offline (قسم 15.6).
- كل سجل في `OutboxTransactions` يحمل: `IdempotencyKey` (يتولّد لحظة الإنشاء الفعلي على الجهاز، متسق مع `00-Project-Overview.md` قسم 14)، نوع العملية، البيانات كاملة (Payload)، وقت الإنشاء المحلي، وحالة المزامنة (`Pending` / `Syncing` / `Failed`).

### 15.3 كشف حالة الاتصال
- مراقبة أحداث `online`/`offline` في المتصفح **+** فحص دوري فعلي (Ping) للـ Backend — حدث المتصفح وحده غير كافٍ (ممكن "متصل" بشبكة محلية بدون إنترنت فعلي للسيرفر).
- شريط حالة دائم وواضح في واجهة الكاشير: "غير متصل — العمليات بتتسجل محليًا".

### 15.4 آلية المزامنة — **قاعدة الحذف الفوري بعد النجاح**
1. لحظة رجوع الاتصال، تبدأ مزامنة تلقائية لكل سجلات `Pending`، **بترتيب إنشائها (FIFO)** قدر الإمكان (مثال: فتح وردية قبل أي فاتورة عليها).
2. كل سجل يُرسَل لـ Endpoint مزامنة مخصص، حاملًا `IdempotencyKey` بتاعه.
3. **عند تأكيد نجاح المزامنة من السيرفر: السجل يُحذف فورًا ونهائيًا من `IndexedDB`.** **لا يُحتفَظ بأي سجل تمت مزامنته بنجاح في التخزين المحلي تحت أي مسمى** — لا "مؤرشف"، لا "مكتمل"، ولا أي حالة وسيطة. قاعدة البيانات الأوفلاين تحتوي **فقط** على المعاملات اللي لسه محتاجة تتبعت فعليًا، ولا حاجة غير كده أبدًا.
4. فشل مؤقت (انقطاع أثناء الإرسال نفسه) → السجل يفضل `Pending` ويُعاد تلقائيًا.
5. رفض منطقي حقيقي من السيرفر (مش تكرار — مثال: تغيّرت قائمة الأسعار) → السجل يتحول لـ `Failed` ويظهر للمراجعة اليدوية، **ولا يُحذف تلقائيًا** في هذه الحالة تحديدًا لأنها تحتاج قرار بشري.

### 15.5 الحماية من التكرار
بما إن كل سجل عنده `IdempotencyKey` ثابت من لحظة الإنشاء، أي محاولة مزامنة متكررة لنفس السجل (انقطاع نص عملية الإرسال، إعادة محاولة يدوية بالغلط) **السيرفر بيتعرف عليها ويرجّع نفس النتيجة الأصلية** بدل تنفيذها تاني — الآلية الكاملة موثّقة في `00-Project-Overview.md` (قسم 14).

### 15.6 مزامنة البيانات المرجعية قبل العمل بدون إنترنت (Reference Data Pre-Sync)

- بيانات مرجعية أساسية للبيع (الأصناف، الوصفات، قوائم الأسعار الفعالة، الخصومات النشطة) تُخزَّن في جدول **`ReferenceDataCache`** منفصل تمامًا عن `OutboxTransactions` (قسم 15.2) — الاتجاه هنا عكسي: بيانات نازلة من السيرفر للجهاز، مش صاعدة منه.
- **هذا الكاش يُحدَّث بشكل استباقي وقت وجود اتصال فعلي** — مش وقت انقطاعه، لأن ساعتها بيبقى الوقت متأخر: عند فتح التطبيق، عند فتح وردية جديدة، وبشكل دوري كل فترة قصيرة (مقترح: كل 15 دقيقة) طالما الجهاز متصل.
- **Delta Sync**: التحديث الدوري يستخدم Endpoint خفيف بيرجّع بس العناصر اللي **اتغيّرت** منذ آخر مزامنة (`GET /api/v1/pos/reference-data?since={lastSyncTimestamp}`) — مش تحميل القائمة كاملة في كل مرة.
- **مؤشر حداثة البيانات**: واجهة الكاشير تعرض بشكل دائم وقت آخر مزامنة ناجحة للبيانات المرجعية (مثال: "آخر تحديث للأسعار: منذ 4 دقائق"). لو الجهاز فضل Offline لفترة تتجاوز حد معيّن (مقترح: أكتر من ساعتين)، يظهر تحذير صريح للكاشير إن الأسعار المعروضة ممكن تكون قديمة — **مع السماح بإتمام البيع رغم التحذير**، لأن استمرارية العمل خلال نافذة الانقطاع أولوية على الدقة الكاملة (نفس فلسفة قسم 20 في `00-Project-Overview.md`).

### 15.7 تحديث المخزون المحلي بعد المزامنة (Post-Sync Inventory Reconciliation)

- أثناء العمل Offline، أي بيع بيخصم من رصيد المخزون **المحلي المخزّن في `ReferenceDataCache`** بشكل تقديري (Optimistic) — الهدف بس إبقاء ميزة "منع البيع عند نفاد الكمية" شغّالة حتى بدون اتصال. الرصيد ده **تقديري وليس نهائيًا**، **مش** لأن فروع تانية بتسحب من نفس المخزون (كل فرع له مخزنه الخاص المستقل — `00-Project-Overview.md` قسم 2)، لكن لأسباب داخل الفرع نفسه:
  - **نقاط بيع/كاشيرين تانيين في نفس الفرع** بيبيعوا من نفس المخزن في نفس الوقت — سواء كانوا متصلين وبيخصموا لحظيًا على السيرفر، أو Offline هما كمان وعندهم نفس التقدير المحلي المستقل بتاعهم.
  - **حركات مخزنية تانية** بتحصل على نفس المخزن بمعزل عن نقاط البيع تمامًا: استلام تحويل وارد، تسوية جرد، استهلاك إنتاج (وصفة بتتحضّر)، أو تسجيل هالك — كل دي ممكن تتسجّل على السيرفر مباشرة لحظة ما الجهاز ده يبقى مقطوع.
- **فور اكتمال مزامنة كل معاملات الـ Outbox بنجاح** (قسم 15.4)، الفرونت **يجب** يعمل تحديث فوري وإجباري لأرصدة المخزون من السيرفر (نداء GetList/GetById طازج، متجاوزًا أي كاش محلي قديم) — **مش الانتظار** لدورة التحديث الدورية العادية (كل 15 دقيقة، قسم 15.6). ده بيصحّح أي انحراف بين التقدير المحلي والرصيد الفعلي على السيرفر فورًا بعد رجوع الاتصال.
- لحد ما التحديث ده يكتمل، أي عملية بيع جديدة في الثواني الأولى بعد رجوع الاتصال قد تفضل تعتمد على القيمة التقديرية القديمة لفترة قصيرة جدًا — احتمال ضئيل، ومقبول كتنازل بسيط في مقابل استمرارية العمل بدون تعقيد إضافي.
