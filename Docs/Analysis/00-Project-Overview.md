# نظام ERP لمحلات الحبّاك (قهوة، بن، عصائر، مياه)
## ملف النظرة العامة على المشروع (Project Overview)

> هذا الملف هو المرجع الأول اللي أي حد (مطوّر، أو Claude Code) لازم يقراه قبل البدء في أي موديول. أي ملف موديول تاني بيُبنى فوق القرارات المكتوبة هنا ولازم يكون متسق معاها. الملف المكمّل له للجزء الأمامي: `00-Frontend-Specs.md`.

## 1. الهدف من النظام

نظام ERP متكامل لإدارة سلسلة محلات قهوة وبن وعصائر ومياه، يغطي الدورة التشغيلية الكاملة:

المشتريات ← المخازن والتصنيع ← المبيعات ونقاط البيع (POS) ← المحاسبة والتقارير المالية ← الامتثال الضريبي المصري (ETA)

مع دعم كامل لتعدد الشركات والفروع، وصلاحيات دقيقة على مستوى الشاشة والحقل، وتكاملات مع أجهزة وأنظمة خارجية.

---

## 2. السياق التجاري (Business Context)

- النظام يخدم **شركة أم واحدة أو أكتر**، وكل شركة ليها **فروع متعددة**.
- كل فرع له: نقطة بيع أو أكتر (POS)، مخزن أو أكتر مرتبط بيه، كاشيرين وموظفين.
- الفرع **لا يطلب توريد من فرع آخر مباشرة** — الطلب دايمًا من المخزن الرئيسي/الإدارة، والتحويل بين الفروع بقرار إداري فقط.
- منتجات النظام تُباع بثلاث طرق تقديم: **صالة (Dine-in) / تيك أواي (Takeaway) / دليفري (Delivery)**، ولكل طريقة تسعير مستقل محتمل.
- الإنتاج له نماذج مختلطة: **لحظي (Real-time)** عند البيع، أو **مخزني (Stocked)**، قابلة للتخصيص على مستوى الشركة/الفرع/نقطة البيع/الصنف.

---

## 3. سياسة الشركات والفروع (Multi-Company / Multi-Branch)

- **قاعدة بيانات واحدة لكل الشركات** (مش قاعدة بيانات منفصلة لكل شركة).
- **نموذج الفصل بين الشركات: Table-per-Company** مع عمود `CompanyId` — وليس Schema-per-Company.
- كل جدول تقريبًا في النظام لازم يحتوي على عمود `CompanyId`، وأغلب الجداول التشغيلية تحتوي كمان على `BranchId`.
- بعض الكيانات ممكن تكون **مشتركة بين الشركات** بشكل صريح وموثّق — دي استثناءات، مش القاعدة العامة.
- **`ICurrentCompanyContext`** بيوفر `CompanyId` الحالي من الـ Claims (قسم 7)، ويُستخدم في **EF Core Global Query Filters**.
- **دفاع إضافي ضد تسريب البيانات بين الشركات**: الاعتماد على الـ Global Query Filter وحده غير كافٍ كخط دفاع أخير — أي Query خام (Raw SQL) أو كود مستقبلي ينسى تفعيل الفلتر عمدًا لسبب ما ممكن يسرّب بيانات شركة تانية. لازم **طبقة تحقق إضافية صريحة** في الـ API Layer (Middleware أو Action Filter) تتأكد إن أي `CompanyId` ظاهر في أي استجابة يطابق شركة المستخدم الحالي، كخط دفاع ثانٍ مستقل عن الفلتر نفسه.

## 4. تعدد اللغات (Localization)

- اللغتين: **العربية (RTL، اللغة الأساسية)** و **الإنجليزية (LTR)**.
- كل مستخدم له **لغة واجهة مفضلة** مسجّلة في حسابه، قابلة للتغيير من إعداداته الشخصية.
- الدعم لازم يكون من الـ Backend مش بس الـ Frontend: رسائل الأخطاء، رسائل الـ Validation، وأسماء الحقول القابلة للترجمة (Resource Files / `.resx` أو مكافئها).
- تنسيق الأرقام والتواريخ والعملات يتبع لغة/إعدادات المستخدم.
- الحقول اللي بتُعرض للعميل مباشرة ممكن تحتاج نسختين (عربي/إنجليزي) مخزّنين على نفس السجل.

### 5.2 تفاصيل التكامل مع منصات التوصيل
- استقبال الطلبات عبر API مع `PlatformOrderId` لمنع التكرار (متسق مع مبدأ الـ Idempotency في قسم 14).
- مزامنة المنيو عبر جدول Mapping مستقل.
- تسوية عمولات دورية آلية (قسم 21 — المهام المجدولة).
- فصل تقارير طلبات المنصات عن الدليفري الداخلي.

### 5.3 تفاصيل التكامل مع مصلحة الضرائب المصرية (ETA)
- يحتاج شهادة توقيع إلكتروني، بروتوكول ETA الرسمي، وربط كود كل صنف بكود GS1/EGS.
- حالات المستند: `Pending` ← `Submitted` ← `Accepted` / `Rejected` / `Failed` / `Cancelled`.
- إعادة محاولة تلقائية بحد أقصى 3 محاولات بفاصل تصاعدي — تُنفَّذ كمهمة مجدولة (قسم 21).

### 5.4 معمارية التكامل مع الأجهزة الفعلية (Local Agent Architecture)
- متصفحات الويب الحديثة تحد بشدة من الوصول المباشر لأجهزة USB/Serial (موازين، ماكينات دفع، طابعات) لأسباب أمنية — الاعتماد على `WebUSB`/`WebSerial` مباشرة من الفرونت **غير موثوق** كحل أساسي (دعم متصفحات محدود جدًا وقيود أمان صارمة).
- **الحل المعتمد**: تطبيق مساعد محلي خفيف (**Local Agent** — خدمة Windows أو تطبيق سطح مكتب صغير) يُثبَّت على جهاز نقطة البيع نفسه، ويوفّر **API محلي** (`http://localhost:{port}`) يتواصل معاه تطبيق الفرونت (الشغّال في المتصفح على نفس الجهاز) لقراءة الميزان، إرسال أمر طباعة، أو التواصل مع ماكينة الدفع.
- الـ Local Agent **مسؤوليته التواصل مع الأجهزة فقط** — لا يحتوي على أي منطق عمل (Business Logic)؛ كل القرارات (صحة السعر، توفر المخزون) تفضل في الـ Backend المركزي كأي عملية عادية.
- عند عدم توفر الـ Local Agent أو تعطّل الجهاز نفسه، الفرونت يسمح بالإدخال اليدوي بصلاحية خاصة (قسم 5.1).

## 6. المستخدمون والمجموعات والصلاحيات

### 6.1 الصلاحيات

نظام صلاحيات بمستويين مستقلين:

1. **صلاحيات النطاق (Scope-Level)**: وصول المستخدم لأكتر من شركة/فرع بدور مختلف في كل نطاق.
2. **صلاحيات الشاشة والحقل (Screen & Field-Level)**: عرض/إضافة/تعديل/حذف على مستوى الشاشة، وصلاحية عرض مستقلة على الحقول الحساسة. الحقول الحساسة اللي المستخدم مالوش صلاحية عرضها **تُستبعد من استجابة الـ API نفسها**.

### 6.2 حماية البيانات الشخصية الحساسة (PII Protection)

مع دخول موديول **شئون العاملين والمرتبات** (قسم 28)، النظام بقى بيمسك بيانات شخصية حساسة على مستوى مختلف تمامًا عن باقي البيانات التشغيلية (الرقم القومي، رقم الحساب البنكي لصرف الراتب، الراتب نفسه، وممكن بيانات تأمين صحي) — دي محتاجة معاملة خاصة غير مجرد صلاحية عرض عادية:

- **تشفير على مستوى العمود (Column-Level Encryption)** إلزامي في قاعدة البيانات لحقول محددة صراحة: الرقم القومي، رقم الحساب البنكي/الآيبان. البيانات دي **لا تُخزَّن كنص صريح (Plain Text)** حتى لو المستخدم اللي بيشوفها عنده صلاحية كاملة.
- **الإخفاء الجزئي الافتراضي (Masking)**: عرض الرقم القومي أو رقم الحساب البنكي في أي شاشة أو تقرير يكون بصيغة مموّهة افتراضيًا (مثال: `••••••••1234`) — إظهار الرقم كامل يتطلب إجراء صريح إضافي (زرار "إظهار") **ويُسجَّل في الـ Audit Trail** كل مرة يحصل فيها، بغض النظر عن إعداد تفعيل الـ Audit العام لهذا الكيان (قسم 18).
- **الاستبعاد من الـ Logging**: أي حقل مصنَّف PII **لا يظهر أبدًا** في نصوص الـ Logging (قسم 22) حتى في مستوى `Debug` — يُستبدل بقيمة مموّهة أو `[REDACTED]` قبل الكتابة في أي سجل.
- **سياسة الاحتفاظ ببيانات الموظفين بعد انتهاء الخدمة**: مقترح — الاحتفاظ الكامل بالسجل لمدة **5 سنوات** بعد تاريخ ترك الخدمة (تماشيًا مع مدد الاحتفاظ المعتادة في القانون المصري لسجلات العمل والتأمينات)، ثم الأرشفة. هذه المدة منفصلة تمامًا عن مدة الاحتفاظ بسجلات الـ Audit المالية (قسم 18) — قرار يحتاج تأكيد نهائي من الفريق القانوني للعميل.

## 7. المصادقة وإدارة الجلسات (Authentication & Session Management)

- **JWT** كآلية مصادقة أساسية، **Access Token** قصير العمر (15-30 دقيقة)، **Refresh Token** أطول عمرًا (7 أيام) مخزّن في HttpOnly Cookie.
- الـ Claims: `UserId`, `CompanyId`, `BranchId`, الأدوار، ولغة الواجهة.
- تسجيل الخروج يُبطل الـ Refresh Token فورًا من جهة السيرفر.
- **تسجيل الدخول من أكتر من جهاز: مسموح دايمًا وبدون أي حد أقصى لعدد الجلسات المتزامنة — قرار محسوم (قسم 29).**

### 8.5 المرفقات والتصدير (Attachments & Export) — سياسة عامة لكل شاشات النظام

**هذه السياسة تنطبق على كل شاشة في كل موديول تتعامل مع مستندات (فواتير، سندات، قيود، عقود...) — لا تُعاد كتابتها في كل ملف موديول.**

**المرفقات (Attachments):**
- متاحة كخيار قياسي في أي شاشة Edit لمستند (`00-Frontend-Specs.md` قسم 7) عبر مكوّن موحّد (`AttachmentsPanel`).
- الأنواع المسموحة: PDF, JPG, PNG, Excel, Word. الحد الأقصى لحجم الملف الواحد: **10 ميجابايت** (قابل للتعديل من الإعدادات — قسم 23). لا يوجد حد لعدد المرفقات لكل مستند.
- **التخزين**: **نظام ملفات محلي على نفس سيرفر الـ VPS** (مثال: `/var/habbak-erp/attachments`) — قرار محسوم (قسم 29)، مع الاحتفاظ بالمسار فقط في قاعدة البيانات. ملحوظة للتنفيذ: يستلزم تخطيط سعة تخزين القرص دوريًا، ولو زاد عدد سيرفرات التطبيق مستقبلًا لازم إعادة النظر (مساحة تخزين مشتركة/شبكية).
- **الأمان**: المرفق يرث **بالضبط** نفس صلاحية عرض المستند الأصلي — لا يوجد صلاحية مستقلة على المرفقات، ولا يمكن الوصول لملف عبر رابط مباشر بدون صلاحية على المستند نفسه.
- **النسخ الاحتياطي**: المرفقات جزء إلزامي من نطاق النسخ الاحتياطي (قسم 24) — نسخ قاعدة البيانات وحدها غير كافٍ.

**التصدير (Export):**
- متاح كإجراء قياسي في كل `DataGrid` وكل شاشة تقرير (`00-Frontend-Specs.md` قسم 4).
- الصيغ المدعومة: **Excel (.xlsx)** كصيغة أساسية للقوائم والتقارير، **PDF** للمستندات الرسمية (فواتير، كشوف حسابات)، **CSV** للاستيراد في أنظمة أخرى، و**طباعة مباشرة**.
- **نطاق التصدير**: البيانات المعروضة حاليًا بعد تطبيق الفلاتر والبحث فقط — وليس كل بيانات الجدول في قاعدة البيانات.
- تنسيق الأرقام والتواريخ في الملف المُصدَّر يتبع لغة المستخدم الحالية (قسم 4).
- **حد الأداء**: تصدير أكتر من **10,000 صف** يتطلب تأكيدًا صريحًا من المستخدم قبل التنفيذ (تفادي إبطاء المتصفح/السيرفر).
- **التصدير الآلي المجدول**: تقارير دورية تُرسَل بالبريد الإلكتروني تلقائيًا، عبر نفس محرك المهام المجدولة (قسم 21) — وليس آلية منفصلة.

## 10. العملات (Multi-Currency)

- كل شركة لها **عملة أساسية مستقلة**، بالإضافة لعملة محلية موحّدة (الجنيه المصري) للتقارير المجمّعة بين الشركات.
- جدول أسعار صرف تاريخي، وكل معاملة تُسجَّل بقيمتها الأصلية + سعر الصرف + القيمة المعادلة بعملة الشركة الأساسية.
- **نفس مبدأ الجدول التاريخي (قيمة + تاريخ سريان)** يُستخدم لأي نسبة قانونية بتتغيّر بقرار حكومي دوري وليس بقرار داخلي — أبرز مثال: شرائح ضريبة كسب العمل ونسب التأمينات الاجتماعية في موديول الرواتب (قسم 28). **لا يُسمح بتثبيت أي نسبة قانونية كقيمة ثابتة في الكود** — تُخزَّن في جدول مؤرَّخ، وأي حساب راتب سابق يفضل يستخدم النسبة اللي كانت سارية وقت احتسابه هو، مش النسبة الحالية.

## 11. محرك الترحيل المحاسبي المركزي (Central Posting Engine)

أي موديول **لا ينشئ قيدًا بنفسه مباشرة** — بينده على `IPostingService.PostAsync(PostingRequest request)`، اللي بيتحقق من التوازن، قواعد الحساب، اكتمال سلسلة الموافقات (قسم 12)، وينشئ القيد داخل نفس الـ Transaction الخاصة بالعملية المصدر. من أمثلة المستهلكين لهذا المحرك (غير المبيعات/المشتريات/POS): **قيد المرتبات الشهري** (موديول شئون العاملين والمرتبات) و**قيد الإهلاك الشهري وقيود صرف/بيع الأصول الثابتة** (موديول الصيانة والأصول الثابتة) — قسم 28.

## 12. محرك سلاسل الموافقات (Approval Workflow Engine)

### 12.1 الفكرة
أي مستند يُربط بسلسلة موافقات (خطوات مرتّبة، كل خطوة معتمد أو أكتر)، عبر شاشة إعدادات (`07-Module-Settings-Permissions.md`).

### 12.2 الكيانات الأساسية
`ApprovalWorkflow`, `ApprovalWorkflowStep` (مع `ApprovalMode`), `ApprovalWorkflowAssignment`, `ApprovalInstance`, `ApprovalAction`.

### 12.3 قواعد العمل
1. لا انتقال لحالة نهائية إلا بعد اجتياز كل الخطوات.
2. **رفض أي خطوة = رفض نهائي** — مستند جديد بالكامل يبدأ سلسلة جديدة.
3. معتمدين متوازيين حسب `ApprovalMode`: `RequireAll` / `RequireMajority` / `RequireAny`.
4. الشاشات بدون سلسلة تفضل بنظام الاعتماد المباشر العادي.
5. فقط صاحب الدور في الخطوة الحالية يقدر يعتمد/يرفض.

### 12.4 التكامل مع محرك الترحيل
`IPostingService` يرفض ترحيل أي مستند لسه مش معتمد بالكامل.

### 12.5 واجهة المستخدم
موثّقة في `00-Frontend-Specs.md` (قسم 18).

## 14. الاتساق عند التكرار (Idempotency)

كل عملية مالية أو مخزنية حساسة (ترحيل قيد، تنفيذ دفع، اعتماد/رفض خطوة موافقة، أو أي عملية معرّضة لإعادة الإرسال — سواء من Retry Policy التلقائي في قسم 20، أو من مزامنة معاملات وضع العمل بدون إنترنت في الفرونت) **لازم تكون Idempotent**: تنفيذها أكتر من مرة بنفس المدخلات **لا يعمل أي أثر مضاعف** (قيد مكرر، دفع مكرر، خصم مخزون مرتين).

### 14.1 آلية `Idempotency Key`
- كل طلب لعملية حساسة يحمل **`IdempotencyKey`** (`Guid`) يتولّد من طرف المُرسِل **وقت إنشاء العملية لأول مرة**، مش وقت كل محاولة إرسال لاحقة.
- جدول `ProcessedIdempotencyKeys` في الـ Backend يخزّن كل مفتاح اتعالج فعلًا، مع نتيجة المعالجة ومعرّف السجل الناتج.
- لو نفس المفتاح وصل تاني، السيرفر **لا يعيد التنفيذ** — يرجّع نفس النتيجة المخزّنة من أول مرة.
- مدة الاحتفاظ بالمفاتيح: مقترح **7 أيام** (تغطي أطول سيناريو Offline محتمل، قسم 14.2) قبل الأرشفة.

### 14.2 التكامل مع وضع العمل بدون إنترنت (Offline Mode)
- كل معاملة تتولّد وهي الجهاز Offline (تفاصيلها الكاملة في `00-Frontend-Specs.md` قسم 15) تحمل `IdempotencyKey` يتولّد **لحظة الإنشاء الفعلي على الجهاز نفسه**، مش لحظة المزامنة لاحقًا.
- بمجرد تأكيد السيرفر نجاح معالجة معاملة معينة، الفرونت **يحذفها فورًا ونهائيًا** من قاعدة بياناته المحلية (تفاصيل كاملة في `00-Frontend-Specs.md` قسم 15.4) — **لا تفضل أي معاملة تمت مزامنتها بنجاح مخزّنة محليًا تحت أي مسمى** (لا "مؤرشفة" ولا غيره). آلية الـ Idempotency Key هنا هي بالظبط اللي بتضمن الأمان حتى لو نفس المعاملة اتبعتت مرتين قبل التأكيد والحذف.

### 14.3 تذاكر مستقلة قابلة للقراءة بدون اتصال (Self-Contained Offline Tickets)

**المشكلة**: بعض محطات العمل في النظام (مثال: تابلت مستشار تصنيع الخلطات في نقاط البيع) **مالهاش بنية تحتية Offline كاملة** (لا `IndexedDB`، لا `OutboxTransactions` — قسم 15 في `00-Frontend-Specs.md`) لأنها أصغر من إنها تستحق التعقيد ده، لكنها محتاجة "تسلّم" معاملة لجهاز تاني (نقطة بيع كاملة) ممكن يكون **هو نفسه Offline** في نفس اللحظة.

**الحل**: بدل ما "التذكرة" (باركود/QR) تحمل مجرد **مرجع (Reference ID)** يحتاج رجوع للسيرفر لمعرفة تفاصيله، التذكرة تحمل **البيانات كاملة مباشرة مُشفَّرة جوّاها** (QR Code — أنسب من الباركود التقليدي لاتساع مساحة البيانات اللي بيقدر يحملها):

- الحمولة (Payload) المشفّرة جوه الـ QR بتحتوي على: تفاصيل الأصناف المطلوبة بكمياتها وأسعارها، **و`IdempotencyKey` (`Guid`) خاص بالتذكرة دي بالذات**، يتولّد وقت إصدار التذكرة نفسها.
- **الجهاز المُصدِر للتذكرة** (تابلت المستشار) **والجهاز القارئ ليها** (نقطة البيع) **الاتنين ميحتاجوش أي اتصال بالإنترنت وقت العملية دي خالص** — التوليد والقراءة بيحصلوا محليًا بالكامل من محتوى الـ QR نفسه.
- **الحماية من الاستخدام المزدوج** تتم بنفس آلية الـ `IdempotencyKey` القياسية (قسم 14.1): لو جهاز القراءة متصل وقت المسح، يتحقق فورًا من السيرفر إن الكود متسجّلش قبل كده. لو Offline وقت المسح، يقبل العملية بثقة زي أي معاملة Offline عادية، والتحقق النهائي بيحصل تلقائيًا وقت المزامنة (قسم 15.4 من `00-Frontend-Specs.md`) — أي تكرار فعلي نادر جدًا (نفس التذكرة اتمسحت في جهازين قبل ما أي منهم يتصل) بيظهر للمراجعة اليدوية بدل ما يتقبل بصمت.
- **هذا النمط عام وليس مقصورًا على مثال الخلطات**: أي محطة عمل خفيفة تحتاج تسليم معاملة لمحطة تانية بدون الاعتماد على اتصال مباشر بينهم أو بالسيرفر وقت التسليم، تقدر تستخدم نفس المبدأ.

## 15. استراتيجية الفهرسة (Database Indexing Strategy)

- فهارس إلزامية على `CompanyId` وتركيبات الفلترة الشائعة فعليًا (`CompanyId, BranchId, Status`).

- Soft Delete افتراضي، Hard Delete استثنائي وموثّق في الـ Audit.
- `IsDeleted` ضمن Global Query Filter تلقائيًا، وتحديث `RowVersion` عند الحذف.

## 17. تعبئة البيانات الأساسية (Data Seeding)

- بيانات ثابتة عبر EF Core Seeding، بيانات بداية كل شركة جديدة (Chart of Accounts Template)، وفصل بيانات التطوير عن الإنتاج.

## 18. سياسة سجل المراجعة (Audit Trail) — اختيارية لكل كيان

- `AuditableEntitiesConfig` + Interceptor مركزي، Cache في الذاكرة، مفعّل افتراضيًا على الكيانات المالية، وجدول `AuditLog` لا يُحذف منه أي سجل أبدًا. **فترة الاحتفاظ المحسومة نهائيًا: 7 سنوات موحّدة لكل سجلات الـ Audit** (بغض النظر عن نوع الكيان — مالي أو تشغيلي)، ثم الأرشفة.

---

## 19. استراتيجية الـ Caching

- **Redis** موزّع. بيانات شبه ثابتة تُخزَّن بمدة 15-30 دقيقة، تقارير ثقيلة بمدة قصيرة. **البيانات المالية اللحظية لا تُخزَّن أبدًا**. إبطال فوري (Event-based).

---

## 20. التعامل مع فشل التكاملات الخارجية (Resilience)

- **Circuit Breaker** و**Retry Policy** عبر **Polly**، مع قائمة انتظار (Queue) عند الفشل المستمر — بدون إيقاف عمل الكاشير أبدًا. أي عملية مُعاد محاولتها لازم تكون Idempotent (قسم 14).

---

## 21. المهام المجدولة والخلفية (Background Jobs)

- **Hangfire** (مقترح مقابل Quartz.NET) لإعادة إرسال ETA، التقارير الدورية، تسوية عمولات المنصات، أرشفة الـ Audit Log. المهام الخلفية المالية تمر بنفس محرك الترحيل وقواعد الـ Concurrency.

---

## 22. الـ Logging والـ Monitoring

- **Serilog** (Structured JSON)، مستويات Information/Warning/Error/Critical، كل Log مالي يحمل `CompanyId/BranchId/UserId/CorrelationId`. **المراقبة: Prometheus + Grafana** (بيئة الاستضافة Contabo VPS ذاتية الإدارة — قسم 29 — فمفيش خدمة مُدارة زي Application Insights أصلاً).

## 23. إدارة الإعدادات (Configuration Management)

- `appsettings.json` للعادي، Environment Variables/Key Vault للحساس، بيئة Sandbox منفصلة لـ ETA، ممنوع أي قيمة سحرية في الكود.

## 24. النسخ الاحتياطي والتعافي من الكوارث (Backup & Disaster Recovery)

- **نسخ احتياطي دوري**: نسخة كاملة يوميًا + نسخ سجل المعاملات (Transaction Log) كل 15-30 دقيقة خلال ساعات العمل.
- **أهداف التعافي (مقترحة، تحتاج تأكيد الفريق)**:
  - **RPO** (أقصى فقدان بيانات مقبول): **15-30 دقيقة**.
  - **RTO** (أقصى وقت لاستعادة النظام): **4 ساعات** خلال ساعات العمل.
- **اختبار الاستعادة (Restore Testing)**: عملية استعادة فعلية (مش مجرد التأكد من وجود ملف النسخة) تُختبر دوريًا (مقترح: شهريًا) على بيئة منفصلة — نسخة لم يُختبر استرجاعها فعليًا لا تُعتبر نسخة موثوقة.
- **مكان التخزين**: منفصل جغرافيًا/تقنيًا عن السيرفر الأساسي.
- **النطاق**: قاعدة البيانات **+** أي ملفات مرفقة مخزّنة خارجها (فواتير ممسوحة، شهادة توقيع ETA) — نسخ قاعدة البيانات وحدها غير كافٍ.
