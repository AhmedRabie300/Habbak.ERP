# Bug-003 — بانل "تفاصيل طلب الشراء" مابيرجعش يعكس الكمية بعد إلغاء/رفض الأمر

> **التاريخ**: 2026-09-25
> **المصدر**: اختبار يدوي على `HabbakErp` الحقيقية بعد Migration بتاعة Remarks7
> **الخطورة**: 🟢 صغيرة — تجميلية بس، البيانات في الداتابيز صح 100%
> **الحالة**: مفتوح

---

## 1. الوصف

**السيناريو**:
1. أمر شراء `PO-00010` اتعمل من طلب شراء `PR-00010` بكمية 1000، بعدين اتعدّل لـ 600.
2. المستخدم فتح الأمر وضغط "إلغاء الأمر" → أكّد الإلغاء.
3. **الداتابيز صح 100%**: `PurchaseRequestLine.OrderedQuantity` رجعت لـ 0، `PurchaseRequest.Status` رجعت لـ `Approved`.
4. **لكن بانل "تفاصيل طلب الشراء"** (تحت شاشة الأمر نفسه) فضل عارض "في الأمر ده: 600" (بدل 0) — رغم إن "لسه مامتطلبش: 1,000" ظهرت صح.

---

## 2. السبب الجذري

`GetPurchaseOrderSourceRequestQuery.cs` بيحسب `OnThisOrderBaseQuantity` من سطور **نفس الأمر** (`PurchaseOrderId == order.Id`) **من غير فلترة بحالة الأمر نفسه**:

```csharp
var onThisOrder = await db.PurchaseOrderLines.AsNoTracking()
    .Where(l => l.PurchaseOrderId == order.Id && l.PurchaseRequestLineId != null)
    .Select(l => new { RequestLineId = l.PurchaseRequestLineId!.Value, l.BaseQuantity })
    .ToListAsync(cancellationToken);
```

يعني بيعرض "السطر بيقول إيه" بغض النظر عن كون الأمر اتلغى أو اترفض. الحساب القديم (قبل Remarks7، بالحساب الديناميكي) كان بيستبعد الأوامر الملغية/المرفوضة من "في الأمر ده" برضه، مش بس من "في أوامر تانية".

`OrderedElsewhereBaseQuantity` (`= Math.Max(0, OrderedQuantity × UnitFactor - OnThis)`) و`RemainingBaseQuantity` (`= Math.Max(0, RequestedBaseQuantity - OrderedQuantity × UnitFactor)`) **بيتحسبوا صح** لأنهم بيعتمدوا على `PurchaseRequestLine.OrderedQuantity` المحفوظ مباشرة، مش على `onThisOrder` — فده اللي خلّى "المتبقي" يظهر صح رغم إن "في الأمر ده" غلط.

## 3. الأثر

| البُعد | التفصيل |
|---|---|
| **الأداء** | 🟢 UI بس — الحسابات الفعلية (الكاب، الحالة) صح 100% |
| **التكرار** | يحصل في أي مرة حد يفتح بانل أمر شراء ملغي/مرفوض كان مرتبط بطلب |
| **التأثير المالي** | ولا حاجة — مفيش قرار بيتاخد بناءً على الرقم الغلط ده لوحده (السقف والحالة بيعتمدوا على العمود المحفوظ مباشرة) |
| **Workaround** | تجاهل "في الأمر ده" لو الأمر حالته ملغي/مرفوض، والاعتماد على "لسه مامتطلبش" (صح دايمًا) |

## 4. الحل المقترح

إضافة فلتر بحالة الأمر على استعلام `onThisOrder`، بنفس نمط الاستبعاد القديم:

```csharp
var onThisOrder = await db.PurchaseOrderLines.AsNoTracking()
    .Where(l => l.PurchaseOrderId == order.Id && l.PurchaseRequestLineId != null
                && order.Status != PurchaseOrderStatus.Cancelled && order.Status != PurchaseOrderStatus.Rejected)
    .Select(...)
```

(أو فحص `order.Status` مرة واحدة قبل الاستعلام، وتفضية `onThisOrder` لو الأمر ملغي/مرفوض.)

---

## 5. سؤال مفتوح قبل التنفيذ

هل "في الأمر ده" المفروض:
- **(أ) تفضل 0 لما الأمر يتلغي** (زي السلوك القديم) — الأمر مالهوش قيمة دلوقتي، مفيش داعي يتعرض كإنه لسه بيحجز كمية.
- **(ب) تفضل عارضة الكمية القديمة** (السلوك الحالي) — معلومة تاريخية مفيدة ("الأمر ده كان طالب كام قبل ما يتلغي")، مع الاعتماد على "لسه مامتطلبش" كمصدر الحقيقة للمتبقي.

القرار محتاج توجيه من صاحب المنتج قبل التنفيذ.

---

## 6. الاختبارات المطلوبة (بعد القرار)

1. أمر شراء اتلغى بعد ما اتحوّل جزئيًا من طلب → البانل يعرض "في الأمر ده" حسب القرار المتخذ (0 أو القيمة القديمة).
2. أمر شراء اترفض بعد نفس السيناريو → نفس السلوك.
3. أمر شراء لسه Draft/Confirmed (مش ملغي/مرفوض) → "في الأمر ده" يفضل زي ما هو (مفيش تغيير في السلوك ده).
