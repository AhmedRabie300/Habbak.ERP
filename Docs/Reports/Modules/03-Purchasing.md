## 2. الدورة الكاملة

```
طلب شراء ──► طلب عروض أسعار ──► أمر شراء ──► إذن استلام ──► فاتورة ──► [سند صرف]
(اختياري)      (اختياري)                          ↕ (الاتجاهان)
```

### 2.1 طلب الشراء
```
مسودة ──submit──► بانتظار الاعتماد ──approve──► معتمد ──► محوَّل (Converted)
                                            ↘ مرفوض  ↘ ملغي
```

### 2.2 طلب عروض الأسعار
```
مسودة ──Send──► مُرسل ──[SetRFQSupplierQuote × n]──► قيد المراجعة ──Award──► تم الترسية
                                                                        ↘ ملغي
```
كل مورد ليه حالة مستقلة: `Pending` / `Responded` / `Declined`.

### 2.3 أمر الشراء
```
مسودة ──Send──► مُرسل ──Confirm──► مؤكد ──► مستلم جزئيًا ──► مستلم كليًا ──► مفوتر ──► مقفول
                                      ↘ مرفوض  ↘ ملغي
```
`PartiallyReceived` / `FullyReceived` **بتتحسبوا تلقائيًا** عند ترحيل إذن الاستلام، بمقارنة
`ReceivedQuantity` بالكمية المطلوبة على كل سطر.

### 2.4 إذن الاستلام — **هنا المخزون بيتحرك**
```
مسودة ──PostGoodsReceipt──► مرحّل
      ↘ ملغي
```

**الترحيل بيعمل**:
- `AcceptedQuantity` → دخول لمخزن الإذن (`TransactionType.Purchase`)
- `RejectedQuantity` → دخول لـ**مخزن التالف** المحدد على السطر — البضاعة المرفوضة **وصلت فعلًا**،
  بس محجورة مش مضافة للمخزون القابل للبيع
- تحديث `ReceivedQuantity` على أمر الشراء وإعادة حساب حالته

> **`RejectedReason` و`RejectedWarehouseId` إلزاميان** لو فيه كمية مرفوضة.

**🆕 مصدر الإذن بقى مرن (G-3)**: الإذن بيرتبط بـ**مصدر واحد بالظبط** — أمر شراء **أو** فاتورة
مباشرة. قبل كده `PurchaseOrderId` كان إلزامي، فنمط "فاتورة فقط" كان **بيوقف تمامًا** عند تحريك
المخزون.

### 2.5 فاتورة الشراء
```
مسودة ──submit──► بانتظار الاعتماد ──post──► مرحّلة ──► مدفوعة جزئيًا ──► مدفوعة
                                         ↘ مرفوضة  ↘ ملغاة
```

**الترحيل بيعمل**:
- تغيير الحالة لـ`Posted`
- **سطر في `SupplierPriceHistory` لكل بند** — سجل دائم مبيتعكسش حتى لو الفاتورة اتلغت بمرتجع
- ❌ **مفيش قيد محاسبي** (`JournalEntryId` بيفضل null)
- ❌ **مفيش حركة مخزون** — دي مسؤولية إذن الاستلام وحده

**الوصول لـ`PartiallyPaid`/`Paid`** بيحصل من **سند الصرف** في موديول الحسابات، مش من هنا.

### 2.6 مرتجع المشتريات
```
مسودة ──PostPurchaseReturn──► مرحّل ↘ ملغي
```

## 3. إعدادات الدورة — `PurchaseCycleSettings`

| الفلاج | الأثر |
|---|---|
| `RequiresPurchaseRequest` / `RequiresQuotation` / `RequiresPurchaseOrder` | بوابات الخطوات |
| **`AllowInvoiceWithoutOrder`** | **بيحدد إن كان نمط "فاتورة فقط" مسموح** — `false` بيرفض بـ`PUR-INVOICE-ORDER-REQUIRED` |
| `RequiresApprovalForInvoice` | لو `true`، الترحيل من `Draft` **مرفوض** — لازم `submit` الأول |
| **`AutoCreateReceiptOnInvoicePost`** 🆕 | ترحيل الفاتورة **بيرسم إذن استلام Draft** |
| **`AutoCreateInvoiceOnReceipt`** 🆕 | ترحيل الإذن **بيرسم فاتورة Draft** |

> ⚠️ **الـendpoint بتاع الإعدادات Upsert كامل بدون دلالات PATCH** — لازم `GET` الأول وإرجاع كل
> الحقول، وإلا هتتصفّر.

## 4. الفلاجان الآليان (كانوا G-6)

الاتنين كانوا **متخزّنين ومتعرضين في الـAPI ومفيش كود بيقراهم**. دلوقتي شغّالين:

| الاتجاه | السلوك |
|---|---|
| **استلام ← فاتورة** | بالكمية **المقبولة بس** (المرفوض وصل بس اتحجر، فمالوش لازمة على مديونية)، وتاريخ الاستحقاق من شروط المورد |
| **فاتورة ← استلام** | بالكميات المتبقية · المخزن من الفاتورة وإلا من `Supplier.DefaultWarehouseId` · **بيرمي خطأ واضح** لو مفيش ولا واحد |

> **الاتنين بيرسموا مستند `Draft` مش `Posted`** — الفاتورة بتقول اشترينا إيه، بس **المخزن وحده**
> اللي يقدر يقول وصل إيه وبأي حالة. الترحيل التلقائي كان هيحرّك مخزون محدّش شافه.

## 5. ملاحظات

| # | الملاحظة |
|---|---|
| 1 | ❌ **مفيش أي قيد محاسبي** من أي مستند مشتريات — مقصود ومتسق مع باقي الموديولات. |
| 2 | `PendingPayment` و`Overdue` **غير قابلين للوصول** — معرّفين لاكتمال الـschema بس. |
| 3 | الفاتورة **مالهاش أثر مخزني إطلاقًا** — الفصل ده مقصود: الفاتورة حدث **مالي**، والاستلام حدث **مادي**. |
| 4 | `SupplierPriceHistory` **append-only** — مبيتعدّلش ولا يتعكس أبدًا، زي أي سجل ورقي. |
