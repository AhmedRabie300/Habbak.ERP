## 1. الهدف من النظام

نظام ERP متكامل لإدارة سلسلة محلات قهوة وبن وعصائر ومياه، يغطي الدورة التشغيلية الكاملة:

المشتريات ← المخازن والتصنيع ← المبيعات ونقاط البيع (POS) ← المحاسبة والتقارير المالية ← الامتثال الضريبي المصري (ETA)

مع دعم كامل لتعدد الشركات والفروع، وصلاحيات دقيقة على مستوى الشاشة والحقل، وتكاملات مع أجهزة وأنظمة خارجية.

---

## 2. السياق التجاري (Business Context)

- النظام يخدم **شركة أم واحدة أو أكتر**، وكل شركة ليها **فروع متعددة**.
- كل فرع له: نقطة بيع أو أكتر (POS)، مخزن أو أكتر مرتبط بيه، كاشيرين وموظفين.
- الفرع **لا يطلب توريد من فرع آخر مباشرة** — الطلب دايمًا من المخزن الرئيسي/الإدارة، والتحويل بين الفروع بقرار إداري فقط.
- منتجات النظام تُباع بثلاث طرق تقديم: **صالة (Dine-in) / تيك أواي (Takeaway) / دليفري (Delivery)**، ولكل طريقة تسعير مستقل محتمل.
- الإنتاج له نماذج مختلطة: **لحظي (Real-time)** عند البيع، أو **مخزني (Stocked)**، قابلة للتخصيص على مستوى الشركة/الفرع/نقطة البيع/الصنف.

---

## 3. سياسة الشركات والفروع (Multi-Company / Multi-Branch)

- **قاعدة بيانات واحدة لكل الشركات** (مش قاعدة بيانات منفصلة لكل شركة).
- **نموذج الفصل بين الشركات: Table-per-Company** مع عمود `CompanyId` — وليس Schema-per-Company.
- كل جدول تقريبًا في النظام لازم يحتوي على عمود `CompanyId`، وأغلب الجداول التشغيلية تحتوي كمان على `BranchId`.
- بعض الكيانات ممكن تكون **مشتركة بين الشركات** بشكل صريح وموثّق — دي استثناءات، مش القاعدة العامة.
- **`ICurrentCompanyContext`** بيوفر `CompanyId` الحالي من الـ Claims (قسم 7)، ويُستخدم في **EF Core Global Query Filters**.
- **دفاع إضافي ضد تسريب البيانات بين الشركات**: الاعتماد على الـ Global Query Filter وحده غير كافٍ كخط دفاع أخير — أي Query خام (Raw SQL) أو كود مستقبلي ينسى تفعيل الفلتر عمدًا لسبب ما ممكن يسرّب بيانات شركة تانية. لازم **طبقة تحقق إضافية صريحة** في الـ API Layer (Middleware أو Action Filter) تتأكد إن أي `CompanyId` ظاهر في أي استجابة يطابق شركة المستخدم الحالي، كخط دفاع ثانٍ مستقل عن الفلتر نفسه.

## 4. تعدد اللغات (Localization)

- اللغتين: **العربية (RTL، اللغة الأساسية)** و **الإنجليزية (LTR)**.
- كل مستخدم له **لغة واجهة مفضلة** مسجّلة في حسابه، قابلة للتغيير من إعداداته الشخصية.
- الدعم لازم يكون من الـ Backend مش بس الـ Frontend: رسائل الأخطاء، رسائل الـ Validation، وأسماء الحقول القابلة للترجمة (Resource Files / `.resx` أو مكافئها).
- تنسيق الأرقام والتواريخ والعملات يتبع لغة/إعدادات المستخدم.
- الحقول اللي بتُعرض للعميل مباشرة ممكن تحتاج نسختين (عربي/إنجليزي) مخزّنين على نفس السجل.

### 5.2 تفاصيل التكامل مع منصات التوصيل
- استقبال الطلبات عبر API مع `PlatformOrderId` لمنع التكرار (متسق مع مبدأ الـ Idempotency في قسم 14).
- مزامنة المنيو عبر جدول Mapping مستقل.
- تسوية عمولات دورية آلية (قسم 21 — المهام المجدولة).
- فصل تقارير طلبات المنصات عن الدليفري الداخلي.

### 5.3 تفاصيل التكامل مع مصلحة الضرائب المصرية (ETA)
- يحتاج شهادة توقيع إلكتروني، بروتوكول ETA الرسمي، وربط كود كل صنف بكود GS1/EGS.
- حالات المستند: `Pending` ← `Submitted` ← `Accepted` / `Rejected` / `Failed` / `Cancelled`.
- إعادة محاولة تلقائية بحد أقصى 3 محاولات بفاصل تصاعدي — تُنفَّذ كمهمة مجدولة (قسم 21).

### 5.4 معمارية التكامل مع الأجهزة الفعلية (Local Agent Architecture)
- متصفحات الويب الحديثة تحد بشدة من الوصول المباشر لأجهزة USB/Serial (موازين، ماكينات دفع، طابعات) لأسباب أمنية — الاعتماد على `WebUSB`/`WebSerial` مباشرة من الفرونت **غير موثوق** كحل أساسي (دعم متصفحات محدود جدًا وقيود أمان صارمة).
- **الحل المعتمد**: تطبيق مساعد محلي خفيف (**Local Agent** — خدمة Windows أو تطبيق سطح مكتب صغير) يُثبَّت على جهاز نقطة البيع نفسه، ويوفّر **API محلي** (`http://localhost:{port}`) يتواصل معاه تطبيق الفرونت (الشغّال في المتصفح على نفس الجهاز) لقراءة الميزان، إرسال أمر طباعة، أو التواصل مع ماكينة الدفع.
- الـ Local Agent **مسؤوليته التواصل مع الأجهزة فقط** — لا يحتوي على أي منطق عمل (Business Logic)؛ كل القرارات (صحة السعر، توفر المخزون) تفضل في الـ Backend المركزي كأي عملية عادية.
- عند عدم توفر الـ Local Agent أو تعطّل الجهاز نفسه، الفرونت يسمح بالإدخال اليدوي بصلاحية خاصة (قسم 5.1).

## 6. المستخدمون والمجموعات والصلاحيات

### 6.1 الصلاحيات

نظام صلاحيات بمستويين مستقلين:

1. **صلاحيات النطاق (Scope-Level)**: وصول المستخدم لأكتر من شركة/فرع بدور مختلف في كل نطاق.
2. **صلاحيات الشاشة والحقل (Screen & Field-Level)**: عرض/إضافة/تعديل/حذف على مستوى الشاشة، وصلاحية عرض مستقلة على الحقول الحساسة. الحقول الحساسة اللي المستخدم مالوش صلاحية عرضها **تُستبعد من استجابة الـ API نفسها**.

### 6.2 حماية البيانات الشخصية الحساسة (PII Protection)

مع دخول موديول **شئون العاملين والمرتبات** (قسم 28)، النظام بقى بيمسك بيانات شخصية حساسة على مستوى مختلف تمامًا عن باقي البيانات التشغيلية (الرقم القومي، رقم الحساب البنكي لصرف الراتب، الراتب نفسه، وممكن بيانات تأمين صحي) — دي محتاجة معاملة خاصة غير مجرد صلاحية عرض عادية:

- **تشفير على مستوى العمود (Column-Level Encryption)** إلزامي في قاعدة البيانات لحقول محددة صراحة: الرقم القومي، رقم الحساب البنكي/الآيبان. البيانات دي **لا تُخزَّن كنص صريح (Plain Text)** حتى لو المستخدم اللي بيشوفها عنده صلاحية كاملة.
- **الإخفاء الجزئي الافتراضي (Masking)**: عرض الرقم القومي أو رقم الحساب البنكي في أي شاشة أو تقرير يكون بصيغة مموّهة افتراضيًا (مثال: `••••••••1234`) — إظهار الرقم كامل يتطلب إجراء صريح إضافي (زرار "إظهار") **ويُسجَّل في الـ Audit Trail** كل مرة يحصل فيها، بغض النظر عن إعداد تفعيل الـ Audit العام لهذا الكيان (قسم 18).
- **الاستبعاد من الـ Logging**: أي حقل مصنَّف PII **لا يظهر أبدًا** في نصوص الـ Logging (قسم 22) حتى في مستوى `Debug` — يُستبدل بقيمة مموّهة أو `[REDACTED]` قبل الكتابة في أي سجل.
- **سياسة الاحتفاظ ببيانات الموظفين بعد انتهاء الخدمة**: مقترح — الاحتفاظ الكامل بالسجل لمدة **5 سنوات** بعد تاريخ ترك الخدمة (تماشيًا مع مدد الاحتفاظ المعتادة في القانون المصري لسجلات العمل والتأمينات)، ثم الأرشفة. هذه المدة منفصلة تمامًا عن مدة الاحتفاظ بسجلات الـ Audit المالية (قسم 18) — قرار يحتاج تأكيد نهائي من الفريق القانوني للعميل.

## 7. المصادقة وإدارة الجلسات (Authentication & Session Management)

- **JWT** كآلية مصادقة أساسية، **Access Token** قصير العمر (15-30 دقيقة)، **Refresh Token** أطول عمرًا (7 أيام) مخزّن في HttpOnly Cookie.
- الـ Claims: `UserId`, `CompanyId`, `BranchId`, الأدوار، ولغة الواجهة.
- تسجيل الخروج يُبطل الـ Refresh Token فورًا من جهة السيرفر.
- **تسجيل الدخول من أكتر من جهاز: مسموح دايمًا ومن غير حد أقصى لعدد الجلسات المتزامنة. قرار محسوم (قسم 29).**

## 8. المعمارية التقنية (Technical Architecture)

### 8.1 الـ Stack
- **.NET Core** (أحدث LTS مستقر وقت التنفيذ)، **SQL Server**، **EF Core Code First**.
- مقترح: **MediatR**, **FluentValidation**, **Mapster/AutoMapper**.
- الفرونت (React) موثّق في `00-Frontend-Specs.md`.

### 8.2 نمط البناء: Modular Monolith
موديولات منفصلة داخل نفس الـ Solution، تتواصل عبر Interfaces واضحة (`IInventoryService`, `IPostingService`, `IApprovalWorkflowService`).

### 8.3 طبقات Clean Architecture

```
src/
├── Habbak.ERP.Domain/          → Entities, Value Objects, Business Rules
├── Habbak.ERP.Application/     → Use Cases, DTOs, Interfaces, Validation
├── Habbak.ERP.Infrastructure/  → EF Core, التكاملات الخارجية، تخزين الملفات
├── Habbak.ERP.API/             → Controllers, Middleware, Auth
└── Habbak.ERP.Shared/          → Constants, Enums, Extensions
```

### 8.5 المرفقات والتصدير (Attachments & Export) — سياسة عامة لكل شاشات النظام

**هذه السياسة تنطبق على كل شاشة في كل موديول تتعامل مع مستندات (فواتير، سندات، قيود، عقود...) — لا تُعاد كتابتها في كل ملف موديول.**

**المرفقات (Attachments):**
- متاحة كخيار قياسي في أي شاشة Edit لمستند (`00-Frontend-Specs.md` قسم 7) عبر مكوّن موحّد (`AttachmentsPanel`).
- الأنواع المسموحة: PDF, JPG, PNG, Excel, Word. الحد الأقصى لحجم الملف الواحد: **10 ميجابايت** (قابل للتعديل من الإعدادات — قسم 23). لا يوجد حد لعدد المرفقات لكل مستند.
- **التخزين**: **نظام ملفات محلي على نفس سيرفر الـ VPS** (مثال: `/var/habbak-erp/attachments`)، والمسار بس اللي بيتحفظ في قاعدة البيانات. **قرار محسوم (قسم 29).** ملحوظة للتنفيذ: محتاج تخطيط دوري لسعة القرص، ولو عدد سيرفرات التطبيق زاد بعدين لازم القرار يتراجع (تخزين مشترك أو شبكي).
  - **⚠️ تباين مع الكود الحالي**: `src/Habbak.ERP.Domain/Common/Attachment.cs` بيخزّن الملف نفسه **جوه SQL Server** (`Content` نوعه `varbinary(max)`) مش على نظام الملفات. التحويل لنظام الملفات محتاج Migration لنقل الملفات الموجودة، **وماتقررش لسه إمتى يتنفّذ**.
- **الأمان**: المرفق يرث **بالضبط** نفس صلاحية عرض المستند الأصلي — لا يوجد صلاحية مستقلة على المرفقات، ولا يمكن الوصول لملف عبر رابط مباشر بدون صلاحية على المستند نفسه.
- **النسخ الاحتياطي**: المرفقات جزء إلزامي من نطاق النسخ الاحتياطي (قسم 24) — نسخ قاعدة البيانات وحدها غير كافٍ.

**التصدير (Export):**
- متاح كإجراء قياسي في كل `DataGrid` وكل شاشة تقرير (`00-Frontend-Specs.md` قسم 4).
- الصيغ المدعومة: **Excel (.xlsx)** كصيغة أساسية للقوائم والتقارير، **PDF** للمستندات الرسمية (فواتير، كشوف حسابات)، **CSV** للاستيراد في أنظمة أخرى، و**طباعة مباشرة**.
- **نطاق التصدير**: البيانات المعروضة حاليًا بعد تطبيق الفلاتر والبحث فقط — وليس كل بيانات الجدول في قاعدة البيانات.
- تنسيق الأرقام والتواريخ في الملف المُصدَّر يتبع لغة المستخدم الحالية (قسم 4).
- **حد الأداء**: تصدير أكتر من **10,000 صف** يتطلب تأكيدًا صريحًا من المستخدم قبل التنفيذ (تفادي إبطاء المتصفح/السيرفر).
- **التصدير الآلي المجدول**: تقارير دورية تُرسَل بالبريد الإلكتروني تلقائيًا، عبر نفس محرك المهام المجدولة (قسم 21) — وليس آلية منفصلة.

## 10. العملات (Multi-Currency)

- كل شركة لها **عملة أساسية مستقلة**، بالإضافة لعملة محلية موحّدة (الجنيه المصري) للتقارير المجمّعة بين الشركات.
- جدول أسعار صرف تاريخي، وكل معاملة تُسجَّل بقيمتها الأصلية + سعر الصرف + القيمة المعادلة بعملة الشركة الأساسية.
- **نفس مبدأ الجدول التاريخي (قيمة + تاريخ سريان)** يُستخدم لأي نسبة قانونية بتتغيّر بقرار حكومي دوري وليس بقرار داخلي — أبرز مثال: شرائح ضريبة كسب العمل ونسب التأمينات الاجتماعية في موديول الرواتب (قسم 28). **لا يُسمح بتثبيت أي نسبة قانونية كقيمة ثابتة في الكود** — تُخزَّن في جدول مؤرَّخ، وأي حساب راتب سابق يفضل يستخدم النسبة اللي كانت سارية وقت احتسابه هو، مش النسبة الحالية.

## 11. محرك الترحيل المحاسبي المركزي (Central Posting Engine)

أي موديول **لا ينشئ قيدًا بنفسه مباشرة** — بينده على `IPostingService.PostAsync(PostingRequest request)`، اللي بيتحقق من التوازن، قواعد الحساب، اكتمال سلسلة الموافقات (قسم 12)، وينشئ القيد داخل نفس الـ Transaction الخاصة بالعملية المصدر. من أمثلة المستهلكين لهذا المحرك (غير المبيعات/المشتريات/POS): **قيد المرتبات الشهري** (موديول شئون العاملين والمرتبات) و**قيد الإهلاك الشهري وقيود صرف/بيع الأصول الثابتة** (موديول الصيانة والأصول الثابتة) — قسم 28.

## 12. محرك سلاسل الموافقات (Approval Workflow Engine)

### 12.1 الفكرة
أي مستند يُربط بسلسلة موافقات (خطوات مرتّبة، كل خطوة معتمد أو أكتر)، عبر شاشة إعدادات (`07-Module-Settings-Permissions.md`).

### 12.2 الكيانات الأساسية

| الكيان | الدور |
|---|---|
| `Screen` | **جديد — Registry موحّد لكل شاشات النظام** (100+ شاشة)، مصدر واحد يتشاور عليه محرك الترحيل (`PostingTemplate.ScreenId`) ومحرك الموافقات (`ApprovalWorkflowAssignment.ScreenId`) معًا — **بدل ما كل محرك يعمل مطابقة نصية (`ScreenCode` كنص) بطريقته الخاصة**. الحقول: `Id`, `Code` (فريد، ثابت)، `NameAr`/`NameEn`، `ModuleCode`. |
| `ApprovalWorkflow` | السلسلة — `Id`, `CompanyId`, `Code`, `NameAr`/`NameEn`, **`VersionNumber`/`PreviousVersionId`/`IsCurrentVersion`** (إلزامي — نفس نمط `PostingTemplate` بالحرف، `00-Posting-Engine-Architecture.md` قسم 3.1؛ تعديل سلسلة مُستخدَمة فعليًا ينشئ إصدارًا جديدًا، والقديم يفضل موجودًا لتفسير الطلبات التاريخية). |
| `ApprovalWorkflowStep` | خطوة في السلسلة — `StepOrder`, `Mode` (`ApprovalStepMode`, تحت). |
| `ApprovalStepApprover` | **جديد — كيان منفصل** (كان مضغوطًا جوه `ApprovalWorkflowStep` سابقًا) — يسمح بأكتر من معتمد لكل خطوة بأنواع مختلفة معًا. الحقول: `Id`, `ApprovalWorkflowStepId`, `ApproverType` (`ApprovalApproverType`, تحت), `ApproverReferenceId` (`long?` — يُستخدم لو `ApproverType = SpecificEmployee` أو `JobGrade`، ويبقى `null` لو `DirectManager` لأنه بيتحل ديناميكيًا). |
| `ApprovalWorkflowAssignment` | ربط `ScreenId` (وليس نص) بسلسلة، مع شرط تفعيل اختياري. |
| `ApprovalInstance` | تتبّع تنفيذ السلسلة — يحمل `WorkflowVersionNumber` المُستخدَم فعليًا (Snapshot، اتساقًا مع الإصدارات أعلاه). |
| `ApprovalAction` | سجل كل إجراء فردي (اعتماد/رفض)، بما فيه سبب الرفض الإلزامي. |

### 12.3 Enums

```csharp
public enum ApprovalApproverType
{
    SpecificEmployee = 1,   // موظف بعينه — ApproverReferenceId = EmployeeId
    Role = 2,               // أي مستخدم بدور معيّن — ApproverReferenceId = RoleId
    DirectManager = 3,       // جديد — يُحل ديناميكيًا من Employee.ManagerId وقت التنفيذ الفعلي، مش وقت تصميم السلسلة
    JobGrade = 4,            // جديد — كل موظف على الدرجة الوظيفية دي، ApproverReferenceId = JobGradeId
}

public enum ApprovalStepMode
{
    AnyOne = 1,   // معتمد واحد من معتمدي الخطوة كفاية (يعادل RequireAny سابقًا)
    All = 2,      // كل معتمدي الخطوة لازم يوافقوا (يعادل RequireAll سابقًا)
}
```

> **قرار معماري**: `Sequential` **أُزيلت عمدًا** من `ApprovalStepMode` — الترتيب بين المعتمدين **لا يُنمذَج كـ"Mode" جوه خطوة واحدة**، لأن ده بيتعارض مع مفهوم `StepOrder` الموجود بالفعل لترتيب الخطوات. لو محتاج "معتمد أ يوافق قبل ما ب يشوف الطلب"، الحل الصحيح **خطوتان منفصلتان بترتيب مختلف**، مش Mode ثالث يخلط بين مستويين مختلفين من الترتيب.
>
> `RequireMajority` (من التصميم الأصلي) **أُزيلت أيضًا لتبسيط النطاق الأول** — `AnyOne`/`All` يغطيان الغالبية العظمى من السيناريوهات العملية؛ الأغلبية النسبية ممكن تُضاف لاحقًا لو ظهرت حاجة فعلية ليها.

### 12.4 قواعد العمل
1. لا انتقال لحالة نهائية إلا بعد اجتياز كل الخطوات.
2. **رفض أي خطوة = رفض نهائي** — مستند جديد بالكامل يبدأ سلسلة جديدة.
3. معتمدين متوازيين حسب `ApprovalStepMode`: `AnyOne` / `All` (قسم 12.3).
4. الشاشات بدون سلسلة تفضل بنظام الاعتماد المباشر العادي.
5. فقط صاحب الدور في الخطوة الحالية يقدر يعتمد/يرفض.
6. **نمط قياسي إلزامي لكل الموديولات**: أي كيان يمر بسلسلة موافقات **لازم يحمل قيمة `Rejected` صراحة ضمن Enum الحالة الخاص بيه نفسه** — رفض السلسلة ينعكس تلقائيًا على حالة الكيان المرتبط في نفس الـ Transaction (مش يُسجَّل في `ApprovalInstance.Status` بمعزل عنه).
7. **`Self-Approval Guard` — إلزامي، جديد**: **مستخدم لا يقدر يعتمد/يرفض طلبه هو نفسه تحت أي ظرف**، حتى لو كان بيحمل الدور أو الدرجة الوظيفية المطلوبة للخطوة (مثال: موظف HR بيقدّم طلب سلفة لنفسه وهو نفسه ضمن معتمدي خطوة HR). النظام يتحقق من `ApprovalAction.ActionByUserId ≠ ApprovalInstance.RequestedByUserId` قبل قبول أي إجراء اعتماد، ويرفض المحاولة صراحة لو تطابقوا.
8. **حل `ApproverType = DirectManager` وقت التنفيذ الفعلي فقط، مش وقت تصميم السلسلة** — لو `Employee.ManagerId = null` وقت الحاجة الفعلية للاعتماد، الطلب **لا يُتخطَّى ولا يُرفَض تلقائيًا**، بل يتصعّد لمعتمد احتياطي مُعرَّف على مستوى الشركة (`CompanyDefaultApproverUserId` — إعداد عام) — قرار واعٍ بدل ترك الطلب عالقًا بلا حل أو المخاطرة بتمريره بلا رقابة حقيقية.
9. **`JobGrade` بدون أي موظف مُسنَد لها** حالة خطأ إعداد يجب اكتشافها صراحة (تنبيه إداري)، وليست تُعامَل كتخطٍّ صامت للخطوة.
10. **إجراء يدوي احتياطي إلزامي من الإصدار الأول (قبل بناء `Delegation`/`Escalation` الكاملين)**: صلاحية إدارية خاصة تسمح بإعادة تسكين `ApprovalInstance` معلَّقة لمعتمد آخر يدويًا (مثال: معتمد أصلي في إجازة) — بدون هذا الإجراء، أي معتمد غير متاح يعني طلبات معلَّقة بلا مخرج مهما طال الوقت.
11. **`ApprovalWorkflow` تدعم الإصدارات بنفس نمط `PostingTemplate`** (قسم 12.2) — تعديل سلسلة مُستخدَمة فعليًا لا يُعدِّل نفس السجل، بل ينشئ إصدارًا جديدًا.

## 14. الاتساق عند التكرار (Idempotency)

كل عملية مالية أو مخزنية حساسة (ترحيل قيد، تنفيذ دفع، اعتماد/رفض خطوة موافقة، أو أي عملية معرّضة لإعادة الإرسال — سواء من Retry Policy التلقائي في قسم 20، أو من مزامنة معاملات وضع العمل بدون إنترنت في الفرونت) **لازم تكون Idempotent**: تنفيذها أكتر من مرة بنفس المدخلات **لا يعمل أي أثر مضاعف** (قيد مكرر، دفع مكرر، خصم مخزون مرتين).

### 14.1 آلية `Idempotency Key`
- كل طلب لعملية حساسة يحمل **`IdempotencyKey`** (`Guid`) يتولّد من طرف المُرسِل **وقت إنشاء العملية لأول مرة**، مش وقت كل محاولة إرسال لاحقة.
- جدول `ProcessedIdempotencyKeys` في الـ Backend يخزّن كل مفتاح اتعالج فعلًا، مع نتيجة المعالجة ومعرّف السجل الناتج.
- لو نفس المفتاح وصل تاني، السيرفر **لا يعيد التنفيذ** — يرجّع نفس النتيجة المخزّنة من أول مرة.
- مدة الاحتفاظ بالمفاتيح: مقترح **7 أيام** (تغطي أطول سيناريو Offline محتمل، قسم 14.2) قبل الأرشفة.

### 14.2 التكامل مع وضع العمل بدون إنترنت (Offline Mode)
- كل معاملة تتولّد وهي الجهاز Offline (تفاصيلها الكاملة في `00-Frontend-Specs.md` قسم 15) تحمل `IdempotencyKey` يتولّد **لحظة الإنشاء الفعلي على الجهاز نفسه**، مش لحظة المزامنة لاحقًا.
- بمجرد تأكيد السيرفر نجاح معالجة معاملة معينة، **تُحذف فورًا ونهائيًا فعليًا (Physical Delete)** من قاعدة البيانات المحلية (تفاصيل كاملة في قسم 14.4 وفي `05-Module-POS-Shifts.md` قسم 2.1) — **لا تفضل أي معاملة تمت مزامنتها بنجاح مخزّنة محليًا تحت أي مسمى** (لا "مؤرشفة" ولا `IsSynced = true` مع بقاء السجل). آلية الـ Idempotency Key هنا هي بالظبط اللي بتضمن الأمان حتى لو نفس المعاملة اتبعتت مرتين قبل التأكيد والحذف.

### 14.3 تذاكر مستقلة قابلة للقراءة بدون اتصال (Self-Contained Offline Tickets)

**المشكلة**: بعض محطات العمل في النظام (مثال: تابلت مستشار تصنيع الخلطات في نقاط البيع) **مالهاش بنية تحتية Offline كاملة** لأنها أصغر من إنها تستحق التعقيد ده، لكنها محتاجة "تسلّم" معاملة لجهاز تاني (نقطة بيع كاملة) ممكن يكون **هو نفسه Offline** في نفس اللحظة.

**الحل**: بدل ما "التذكرة" (باركود/QR) تحمل مجرد **مرجع (Reference ID)** يحتاج رجوع للسيرفر لمعرفة تفاصيله، التذكرة تحمل **البيانات كاملة مباشرة مُشفَّرة جوّاها** (QR Code — أنسب من الباركود التقليدي لاتساع مساحة البيانات اللي بيقدر يحملها):

- الحمولة (Payload) المشفّرة جوه الـ QR بتحتوي على: تفاصيل الأصناف المطلوبة بكمياتها وأسعارها، **و`IdempotencyKey` (`Guid`) خاص بالتذكرة دي بالذات**، يتولّد وقت إصدار التذكرة نفسها.
- **الجهاز المُصدِر للتذكرة** (تابلت المستشار) **والجهاز القارئ ليها** (نقطة البيع) **الاتنين ميحتاجوش أي اتصال بالإنترنت وقت العملية دي خالص** — التوليد والقراءة بيحصلوا محليًا بالكامل من محتوى الـ QR نفسه.
- **الحماية من الاستخدام المزدوج** تتم بنفس آلية الـ `IdempotencyKey` القياسية (قسم 14.1): لو جهاز القراءة متصل وقت المسح، يتحقق فورًا من السيرفر إن الكود متسجّلش قبل كده. لو Offline وقت المسح، يقبل العملية بثقة زي أي معاملة Offline عادية، والتحقق النهائي بيحصل تلقائيًا وقت المزامنة (قسم 14.4.1) — أي تكرار فعلي نادر جدًا (نفس التذكرة اتمسحت في جهازين قبل ما أي منهم يتصل) بيظهر للمراجعة اليدوية بدل ما يتقبل بصمت.
- **هذا النمط عام وليس مقصورًا على مثال الخلطات**: أي محطة عمل خفيفة تحتاج تسليم معاملة لمحطة تانية بدون الاعتماد على اتصال مباشر بينهم أو بالسيرفر وقت التسليم، تقدر تستخدم نفس المبدأ.

### 14.4 معمارية قاعدة بيانات الفرع المحلية وآلية التزامن (Branch-Local Database & Sync Mechanism)

**الطوبولوجيا المؤكدة (الوضع الحالي)**: كل فرع مزوَّد بجهاز محلي واحد بس (قابل للتوسعة لاحقًا لأكتر من جهاز، قسم 14.4.4) يحمل **قاعدة بيانات محلية كاملة** (SQL Server Express أو LocalDB — نفس تقنية قاعدة البيانات السحابية، لتوحيد الـ Migrations وتفادي ازدواج أدوات مختلفة) ونسخة محلية من الـ Backend. **الفرونت في نقطة البيع لا يحتاج أي منطق Offline خاص به إطلاقًا** — هو دايمًا بينده على "الـ API الحالي" بس، سواء كان ده الـ API المحلي (وقت انقطاع الاتصال بالسحابة) أو السحابي مباشرة (وقت توفره) — كل تعقيد التزامن مسؤولية الطبقة الخلفية بس، مش الفرونت.

#### 14.4.1 آلية الرفع (محلي ← سحابة)
1. **خدمة تزامن محلية (Local Sync Service)** شغّالة باستمرار على جهاز الفرع (Background Service مستقل عن واجهة نقطة البيع نفسها)، بتفحص دوريًا (كل ثوانٍ لدقيقة تقريبًا) قاعدة البيانات المحلية عن أي حركات لسه محتاجة تترفع.
2. لكل حركة (`Shift`, `Check`, `POSInvoice`, `POSPayment`, `DrawerMovement`...)، نداء لـEndpoint مخصص للمزامنة على السحابة، حاملة `IdempotencyKey` بتاعتها، **بترتيب FIFO** حسب وقت الإنشاء (عشان التسلسل المنطقي زي فتح الوردية قبل أي فاتورة عليها يتحفظ). **الحركات المتعددة تُرسَل في دفعة واحدة (Batch) بدل نداء منفصل لكل حركة** لتقليل عدد نداءات الشبكة، لكن معالجة كل حركة داخل الدفعة تبقى مستقلة (نجاح واحدة لا يعتمد على نجاح البقية).
3. السحابة تعالج الطلب **بنفس منطق الأعمال المُستخدَم في العمليات الأونلاين العادية** (نفس Command Handlers) — لا يوجد "مسار كود خاص بالمزامنة" منفصل عن المسار العادي، فقط نقطة دخول مختلفة.
4. **نجاح الرفع (تأكيد من السحابة) = حذف فوري فعلي (Physical Delete) من قاعدة البيانات المحلية** — لا استثناء (قسم 14.2).
5. **فشل الرفع** (السحابة غير متاحة) = الحركة تفضل في القاعدة المحلية كما هي، وتُعاد المحاولة تلقائيًا بـPolly Retry Policy (قسم 20) في الدورة التالية.

#### 14.4.2 آلية السحب (سحابة ← محلي)
- نفس مبدأ جلب البيانات المرجعية بشكل استباقي واستخدام Delta Sync (`GET /api/v1/pos/reference-data?since={lastSyncTimestamp}`) — منفَّذ بواسطة خدمة التزامن المحلية نفسها على مستوى قاعدة بيانات الفرع كله. **التردد الفعلي يختلف حسب نوع البيانات — تفاصيل كاملة في قسم 14.4.6.**

#### 14.4.3 أمان التزامن في ظل جهاز واحد لكل فرع
بما إن الوضع الحالي جهاز واحد بس لكل فرع، **لا يوجد تضارب تزامن بين أكتر من كاشير على نفس قاعدة البيانات المحلية** — أي تزامن متعدد الكتابة بيتم التعامل معاه بواسطة قواعد الـ Concurrency القياسية لقاعدة البيانات نفسها (قسم 13)، مش بتقدير تفاؤلي منفصل لكل جهاز.

#### 14.4.4 التوافق المستقبلي مع أكتر من جهاز للفرع الواحد
كل الكيانات التشغيلية في `05-Module-POS-Shifts.md` مصمَّمة من الأساس بعمود `POSTerminalId` مباشر — لو الفرع اتوسّع لأكتر من جهاز مستقبلًا، النموذج على مستوى السحابة **لا يحتاج أي تعديل**؛ القرار الوحيد المطلوب وقتها هو معماري بحت: هل الأجهزة الجديدة بتشارك نفس قاعدة البيانات المحلية عبر شبكة داخلية (Local Server واحد يخدم أكتر من جهاز)، أو كل جهاز بقاعدته الخاصة (يتطلب وقتها آلية اتساق إضافية بين الأجهزة المحلية نفسها قبل الرفع للسحابة) — قرار مؤجَّل، غير مطلوب حسمه الآن.

#### 14.4.5 وضع تشغيل نقطة البيع (POS Operation Mode) — إعداد لكل فرع

**كيان جديد**: `BranchPOSSettings.OperationMode` — إعداد صريح لكل فرع يحدد سلوكه الأساسي، بدل افتراض نمط واحد يناسب كل الفروع:

| القيمة | الوصف | يناسب |
|---|---|---|
| `CloudOnly` | **لا توجد قاعدة بيانات محلية إطلاقًا** — نقطة البيع تتصل بالسحابة مباشرة في كل عملية. أي انقطاع إنترنت = توقف كامل للبيع لحد رجوع الاتصال | فروع باتصال إنترنت مستقر وموثوق جدًا، ومحتاجة أبسط نشر ممكن |
| `OfflineOnly` | الفرع بيشتغل محليًا بشكل شبه دائم، والمزامنة **يدوية أو دورية نادرة** (يوميًا مثلًا) بدل مستمرة في الخلفية | فروع نائية باتصال إنترنت شبه منعدم أو غير موثوق إطلاقًا |
| `HybridAutoSync` (الافتراضي والموصى به) | التصميم الكامل الموثَّق في هذا القسم بالكامل — محلي أولًا دايمًا + مزامنة تلقائية مستمرة في الخلفية + حذف فوري بعد الرفع | الغالبية العظمى من الفروع — التوازن الأمثل بين المرونة والاتساق |

- الإعداد ده بيُحدَّد وقت تسجيل الفرع، وقابل للتغيير من شاشة إعدادات الفرع (`07-Module-Settings-Permissions.md`)، لكن **تغييره بعد بدء التشغيل الفعلي عملية استثنائية** تتطلب تدخلًا تقنيًا (نقل بيانات أو تركيب بنية تحتية محلية جديدة)، مش مجرد تبديل قيمة في شاشة.

#### 14.4.6 تردد المزامنة حسب نوع البيانات (Sync Frequency by Data Category)

**ليس كل البيانات المرجعية بنفس درجة الحساسية الزمنية** — تردد سحب مختلف لكل فئة، بدل قيمة واحدة عامة لكل حاجة:

| الفئة | التردد الافتراضي | الآلية | السبب |
|---|---|---|---|
| **المستخدمون والصلاحيات** | **فوري** (إشعار Push) + Polling احتياطي كل دقيقة | SignalR (`00-Frontend-Specs.md` قسم 14) كـ"جرس تنبيه" — الإشعار بيقول لخدمة التزامن "اسحب دلوقتي"، والبيانات الفعلية لسه بتتجاب عبر نداء GetList عادي محترم للصلاحيات | **أمان حرج** — إلغاء صلاحية موظف لازم يوصل فورًا، مش بعد دقايق |
| **الأسعار والخصومات** | كل 5 دقائق + **زرار "مزامنة فورية" يدوي** متاح للإدارة | Delta Sync دوري | حساسية تجارية — تعديل سعر أو بدء عرض يستحق سرعة معقولة |
| **حركات مخزون واردة من مصادر خارج الفرع** (تحويل مُعتمَد من الإدارة المركزية) | كل 10-15 دقيقة | Delta Sync دوري | تشغيلي، مش حرج بنفس درجة الأسعار/الصلاحيات |
| **بيانات مرجعية عامة أخرى** (كتالوج الأصناف، إعدادات عامة) | كل 15 دقيقة | Delta Sync دوري | غير حرج زمنيًا |

- **مبدأ الإشعار الفوري (Push Hint)**: بالنسبة للفئات الحرجة (الصلاحيات تحديدًا)، السحابة بترسل إشعار SignalR فوري لأي فرع متصل حاليًا لحظة حدوث تغيير، بدل ما تستنى دورة الـ Polling العادية. **الإشعار ده تنبيه بس ("في تحديث")، مش ناقل للبيانات نفسها** — البيانات الفعلية لسه بتتجاب عبر نفس مسار الـ API المحترم للصلاحيات والفلترة (نفس مبدأ استخدام SignalR الموثَّق في `00-Frontend-Specs.md` قسم 14 لسلاسل الموافقات).
- **لو الفرع كان Offline وقت الإشعار**: الإشعار بيضيع طبيعيًا (SignalR مش قناة موثوقة للتسليم المؤجَّل)، لكن **دورة الـ Polling الدورية بتضمن الوصول للتحديث عاجلًا أم آجلًا** فور رجوع الاتصال — الإشعار الفوري تحسين للسرعة وقت الاتصال، مش الاعتماد الوحيد.
- التردد الافتراضي لكل فئة **قابل للتخصيص من الإعدادات** (لا يُثبَّت في الكود، `00-Project-Overview.md` قسم 23).

#### 14.4.7 إعدادات الفرع والأجهزة (Branch & Device Configuration)

**كيانات جديدة تعيش رسميًا في `07-Module-Settings-Permissions.md`** (لم يُكتب بعد) لكن موثَّقة هنا مبدئيًا لأنها جزء أساسي من معمارية الفرع المحلي:

| الكيان | الوصف |
|---|---|
| `BranchPOSSettings` | `OperationMode` (قسم 14.4.5)، تردد المزامنة المخصص لكل فئة (قسم 14.4.6) لو مختلف عن الافتراضي |
| `BranchDevice` | سجل الأجهزة الفعلية بالفرع: اسم الجهاز، نوعه (نقطة بيع/شاشة مطبخ)، آخر ظهور نشط، حالة التفعيل |
| `BranchPaymentMachineConfig` | ربط ماكينة دفع بنكي بالفرع — نوع الماكينة/المزوّد فقط (بيانات وصفية) |
| `BranchScaleConfig` | ربط ميزان بالفرع — الموديل ونوع التكامل فقط |

> **مبدأ فصل حاسم**: البيانات **الوصفية/التجارية** لهذه الكيانات (اسم الجهاز، نوع الماكينة، أي فرع) تُخزَّن مركزيًا في السحابة كالمعتاد. أما **تفاصيل الاتصال التقنية المحلية البحتة** (رقم منفذ COM، عنوان IP محلي، مسار قاعدة البيانات المحلية نفسها) **لا تُخزَّن في السحابة إطلاقًا** — تعيش حصريًا في ملف تكوين محلي (`appsettings.json`) على جهاز الفرع نفسه (`00-Project-Overview.md` قسم 23، إدارة الإعدادات) — لأنها بيانات لا معنى لها خارج شبكة الفرع المحلية، ولازم تكون معروفة للجهاز **قبل** أي اتصال بالسحابة أصلًا (مشكلة "البيضة والدجاجة" لو اتخزنت مركزيًا).

## 15. استراتيجية الفهرسة (Database Indexing Strategy)

- فهارس إلزامية على `CompanyId` وتركيبات الفلترة الشائعة فعليًا (`CompanyId, BranchId, Status`).
- توازن مدروس على الجداول عالية الكتابة (حركة المخزون، الـ Audit، القيود).
- مراجعة دورية بناءً على Query Store الفعلي.

---

## 16. سياسة الحذف (Deletion Policy)

- Soft Delete افتراضي، Hard Delete استثنائي وموثّق في الـ Audit.
- `IsDeleted` ضمن Global Query Filter تلقائيًا، وتحديث `RowVersion` عند الحذف.

---

## 17. تعبئة البيانات الأساسية (Data Seeding)

- بيانات ثابتة عبر EF Core Seeding، بيانات بداية كل شركة جديدة (Chart of Accounts Template)، وفصل بيانات التطوير عن الإنتاج.

---

## 18. سياسة سجل المراجعة (Audit Trail) — اختيارية لكل كيان

- `AuditableEntitiesConfig` + Interceptor مركزي، Cache في الذاكرة، مفعّل افتراضيًا على الكيانات المالية، وجدول `AuditLog` لا يُحذف منه أي سجل أبدًا. **فترة الاحتفاظ المحسومة نهائيًا: 7 سنوات موحّدة لكل سجلات الـ Audit** (بغض النظر عن نوع الكيان — مالي أو تشغيلي)، ثم الأرشفة.

---

## 19. استراتيجية الـ Caching

- **Redis** موزّع. بيانات شبه ثابتة تُخزَّن بمدة 15-30 دقيقة، تقارير ثقيلة بمدة قصيرة. **البيانات المالية اللحظية لا تُخزَّن أبدًا**. إبطال فوري (Event-based).

---

## 20. التعامل مع فشل التكاملات الخارجية (Resilience)

- **Circuit Breaker** و**Retry Policy** عبر **Polly**، مع قائمة انتظار (Queue) عند الفشل المستمر — بدون إيقاف عمل الكاشير أبدًا. أي عملية مُعاد محاولتها لازم تكون Idempotent (قسم 14).

---

## 21. المهام المجدولة والخلفية (Background Jobs)

- **Hangfire** (مقترح مقابل Quartz.NET) لإعادة إرسال ETA، التقارير الدورية، تسوية عمولات المنصات، أرشفة الـ Audit Log. المهام الخلفية المالية تمر بنفس محرك الترحيل وقواعد الـ Concurrency.

---

## 22. الـ Logging والـ Monitoring

- **Serilog** (Structured JSON)، مستويات Information/Warning/Error/Critical، كل Log مالي يحمل `CompanyId/BranchId/UserId/CorrelationId`. **المراقبة: Prometheus + Grafana**، لأن الاستضافة على Contabo VPS ذاتية الإدارة (قسم 29)، فمفيش خدمة مُدارة زي Application Insights أصلًا.

---

## 23. إدارة الإعدادات (Configuration Management)

- `appsettings.json` للعادي، Environment Variables/Key Vault للحساس، بيئة Sandbox منفصلة لـ ETA، ممنوع أي قيمة سحرية في الكود.

---

## 24. النسخ الاحتياطي والتعافي من الكوارث (Backup & Disaster Recovery)

- **نسخ احتياطي دوري**: نسخة كاملة يوميًا + نسخ سجل المعاملات (Transaction Log) كل 15-30 دقيقة خلال ساعات العمل.
- **أهداف التعافي (مقترحة، تحتاج تأكيد الفريق)**:
  - **RPO** (أقصى فقدان بيانات مقبول): **15-30 دقيقة**.
  - **RTO** (أقصى وقت لاستعادة النظام): **4 ساعات** خلال ساعات العمل.
- **اختبار الاستعادة (Restore Testing)**: عملية استعادة فعلية (مش مجرد التأكد من وجود ملف النسخة) تُختبر دوريًا (مقترح: شهريًا) على بيئة منفصلة — نسخة لم يُختبر استرجاعها فعليًا لا تُعتبر نسخة موثوقة.
- **مكان التخزين**: منفصل جغرافيًا/تقنيًا عن السيرفر الأساسي.
- **النطاق**: قاعدة البيانات **+** أي ملفات مرفقة مخزّنة خارجها (فواتير ممسوحة، شهادة توقيع ETA) — نسخ قاعدة البيانات وحدها غير كافٍ.

## 25. استراتيجية اختبار الباك إند (Backend Testing Strategy)

| نوع الاختبار | الأداة | النطاق |
|---|---|---|
| اختبارات الوحدة | **xUnit** | منطق `Domain`/`Application` بمعزل تام، بدون قاعدة بيانات |
| اختبارات التكامل | **xUnit** + قاعدة بيانات اختبار منفصلة (Testcontainers/LocalDB) | سلوك `IPostingService` و`IApprovalWorkflowService` فعليًا مع قاعدة بيانات حقيقية |
| اختبارات الـ API | **xUnit** + `WebApplicationFactory` | عقد الـ API وشكل الأخطاء الموحّد (`00-Frontend-Specs.md` قسم 12) |

**قاعدة إلزامية**: أي تعديل على **محرك الترحيل** (قسم 11) أو **محرك سلاسل الموافقات** (قسم 12) **لا يُدمَج بدون اختبارات تكامل تغطي التغيير** — أخطر جزئين في النظام من ناحية الأثر المالي المباشر.
