### 6. الدورات التشغيلية

#### 6.1 دورة التوظيف
طلب توظيف → اعتماد → إعلان → مقابلات → عرض → عقد → تسجيل تأمينات → إنشاء User → Assignment

#### 6.2 دورة الحضور اليومية
بصمة دخول → بصمة خروج → حساب الساعات → الإضافي/التأخير → القيود

##### 6.2.1 قواعد الإضافي (Overtime) — جديد

| النوع | المعدل | الحد الأقصى |
|---|---|---|
| نهار عادي | 1.5× | حسب القانون |
| ليل | 2× | حسب القانون |
| جمعة/عطلة | 2× | حسب القانون |
| عيد رسمي | 3× | حسب القانون |

**القواعد**:
- **موافقة مسبقة من المدير — عبر محرك سلاسل الموافقات المركزي** (`00-Project-Overview.md` قسم 12)، **وليس آلية موافقة منفصلة خاصة بالإضافي** — نفس المبدأ المُلزَم في قسم 5 و9 من هذا البرومبت.
- حد أقصى يومي/شهري (للتأكيد مع المستشار — قسم 3.1).
- مرتبط بـ `TimeEntry`.
- في الـ Payroll → سطر مستقل في `PayrollLine`.

#### 6.3 دورة الإجازات
طلب (Self-Service) → اعتماد (عبر محرك سلاسل الموافقات المركزي — جديد) → خصم من الرصيد → ربط بالراتب → إشعار

#### 6.4 دورة المرتبات الشهرية

حساب الأساسي → + بدلات → + إضافي → - غياب → - جزاءات → - سلف → - تأمينات → - ضريبة → صافي → القيد → إشعار + قسيمة

> **إضافة إلزامية — جديد، حرج**: `PayrollRun` تشغيل شهري آلي بيحسب ويصرف رواتب — **نفس فئة الخطر اللي ظهرت فعليًا في `DepreciationRun` بموديول الأصول الثابتة**: من غير `IdempotencyKey`، إعادة تشغيل الـJob بالخطأ (فشل جزئي، إعادة محاولة يدوية) هتضاعف صرف الرواتب بالكامل. التحليل **لازم** يوضح صراحة: `PayrollRun.IdempotencyKey` مشتق من (الشركة + الشهر + السنة)، وقاعدة عمل تمنع تشغيله مرتين لنفس الشهر (`00-Project-Overview.md` قسم 14.1). ده متطلب تحليلي أساسي مؤثر على تقدير الجهد (قسم 14)، مش تفصيلة تنفيذية تتأجل.

#### 6.5 دورة إنهاء الخدمة
طلب → اعتماد (عبر محرك سلاسل الموافقات) → حساب مستحقات → تسوية عهد → استمارة 6 → قفل حساب → صرف → شهادة خبرة

**أنواع الإنهاء — جديد** (كل نوع له حساب EOS مختلف، تفاصيل الحساب في قسم 3.1، للتأكيد مع المستشار):

| النوع | EOS | إجراءات | استمارة |
|---|---|---|---|
| استقالة | مكافأة + رصيد إجازات | إشعار مسبق (30 يوم) | استمارة 6 |
| إنهاء من الشركة | مكافأة + تعويض | حسب قانون العمل | استمارة 6 |
| معاش | مكافأة + معاش | هيئة التأمينات | استمارة 6 |
| وفاة | للمستحقين | شهادات وفاة + حصر إرث | استمارة 6 |
| نهاية عقد | مكافأة | بدون إشعار | استمارة 6 |

> **ملاحظة معمارية**: `EmployeeEndOfService`/`EOSCalculation` (قسم 5) لازم يحمل حقل `TerminationType` (Enum بالأنواع الخمسة دي) بدل حساب واحد عام — كل نوع بمعادلته الخاصة. قيد نهاية الخدمة الناتج (قسم 9) يمر بـ`IPostingService` بغض النظر عن النوع، لكن الأطراف الدائنة ممكن تختلف (المستحقين بدل الموظف نفسه في حالة الوفاة، مثلًا) — وضّح ده في تصميم القالب.

#### 6.6 دورة السلف (Self-Service)
طلب (Self-Service) → اعتماد المدير → اعتماد HR → صرف → أقساط شهرية → خصم من الراتب

> **ملاحظة**: خطوتا "اعتماد المدير" و"اعتماد HR" = خطوتين متتاليتين في نفس سلسلة الموافقات المركزية، مش كيانين اعتماد منفصلين.

#### 6.7 دورة تحديث البيانات (Self-Service)
الموظف يعدّل → طلب اعتماد (عبر محرك سلاسل الموافقات) → HR يراجع → تحديث → Audit Log

### 7. التكامل مع الموديولات الحالية

لكل موديول — إزاي HR بيتكامل معاه:

| الموديول | التكامل |
|---|---|
| **الإعدادات** | User.EmployeeId → FK، Self-Service Portal كشاشة جديدة — **راجع قسم 2 لحالة نظام الصلاحيات الفعلية أولًا** |
| **المخازن** | CustodyOfficer → Employee FK |
| **المشتريات** | اعتماد طلب/أمر/فاتورة — Employee كـ Approver عبر محرك الموافقات المركزي |
| **المبيعات** | SALES_REP → عمولات، أداء |
| **POS** | الكاشير → Employee، توزيع البقشيش، أداء، ربط Shifts. **قرار مطلوب — مين Source of Truth للحضور؟** (أ) POS Shifts = المصدر، (ب) HR Attendance = المصدر، (ج) تكامل — POS يُسجّل، HR يُقرّ. **رأي موجّه (مش قرار نهائي)**: `Shift.OpenedAtUtc`/`ClosedAtUtc` بيغطي الكاشيرين بس (مش كل الموظفين: مطبخ، مندوب توصيل، محاسب...)، وتوقيت فتح/قفل الوردية مش بالضرورة نفس توقيت الحضور الفعلي (ممكن الموظف يوصل قبل ما يفتح الوردية بربع ساعة). **الخيار (ج) الأقرب معماريًا**: `Attendance`/`TimeEntry` يفضل مصدر الحقيقة الوحيد لكل الموظفين، وبيانات الوردية تُستخدم كـ"تلقيم مبدئي" أو تدقيق تكميلي للكاشيرين تحديدًا، مش بديل كامل. التحليل لازم يحسم ده صراحة مع توضيح التأثير على بنية `Attendance` و`ShiftSchedule`. |
| **الأصول** | TechnicianId → Employee FK |
| **الحسابات** | الموظف كطرف في السندات، السلف، العهد، قيد الرواتب — **بما في ذلك `CostCenterId` إلزامي على قيد الرواتب (راجع قسم 9)** |

### 11. تحليل الخيارات (Build vs Buy)

**اعمل مقارنة**:

| الخيار | المميزات | العيوب |
|---|---|---|
| **Build كامل** | تكامل كامل، تخصيص | وقت، تكلفة |
| **Build جزئي + تكامل مع نظام خارجي** | أسرع، أقل تكلفة | تكامل، Sync |
| **شراء نظام جاهز + تكامل** | سريع، مجرب | تكلفة شهرية، تخصيص محدود |
| **Outsourcing كامل** | مفيش تطوير | تكلفة، اعتماد على مزود |

**توصيتك** لأي خيار + السبب.

### 14. تقدير الجهد

**مقسّم لمراحل**:

| المرحلة | الجهد (يوم) | المخرج |
|---|---|---|
| **HR Core** | 14-20 | Employee + Contracts + Org Structure + ربط كل الموديولات |
| **Attendance + Leave** | 20-30 | بصمة + إجازات + ربط بالرواتب |
| **Payroll** | 30-40 | حساب الرواتب + ضرائب + تأمينات + قيود (بما فيها Idempotency، قسم 6.4) |

| **Integration Refactor** | 10-15 | تعديل الموديولات الحالية لاستخدام Employee |

**الإجمالي**: ~130-180 يوم تطوير (رقم يحتاج تحديث لو Self-Service Portal اتأجلت لمرحلة تانية حسب قسم 2).

## القواعد

- اكتب التحليل **من منظور ERP Consultant**.
- ركّز على **البيزنس والامتثال** مش الكود.
- **كل رقم قانوني** يبقى معلّم إنه "للتأكيد مع المستشار".
- استخدم **جداول مقارنة**.
- **مختصر** لكن شامل (500-700 سطر max).
- **مسارات الملفات الفعلية** لما تذكر الكود.
- **ركز على Self-Service** بشكل خاص (قسم 8) — **لكن بشرط توضيح اعتماديته على نظام الصلاحيات أولًا (قسم 2).**
- **التزم بمحرك سلاسل الموافقات المركزي الموجود ومعايير التسمية الموحّدة — لا تصمم آليات موازية جديدة لهما (قسم 5، 9).**
- لو فيه تناقضات مع التقارير السابقة → وثّقها.
