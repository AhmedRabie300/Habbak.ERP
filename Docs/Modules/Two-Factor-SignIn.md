# التحقق بخطوتين (Two-Factor Sign-In)

**التاريخ:** 2026-09-19 · **Migration:** `20260919131017_TwoFactorSignIn` (اتطبّقت على LocalDB وعلى SQL Server الحقيقي)

`User.TwoFactorEnabled` كان متخزّن ومحدش بيقراه. دلوقتي بقى شغّال فعلًا.

## الطريقة
- **كود من تطبيق مصادقة (TOTP):** Google Authenticator أو Microsoft Authenticator أو أي تطبيق زيهم. الكود 6 أرقام بيتغيّر كل 30 ثانية (RFC 6238). مفيش SMS ولا إيميل، فمش محتاجين أي خدمة خارجية، والتطبيق بيشتغل من غير نت.
- **10 أكواد استرداد** لو الموبايل مش مع المستخدم. كل كود بيشتغل مرة واحدة، وبيظهر للمستخدم مرة واحدة بس، والمتخزّن hash (SHA-256) مش الكود نفسه.
- **المستخدم هو اللي بيشغّله لنفسه.** المدير يقدر **يلغيه** بس (لو الموبايل ضاع)، مايقدرش يشغّله بدل المستخدم.

## الدخول
1. `POST /auth/login`: لو التحقق مقفول بيرجع الجلسة زي الأول. لو شغّال، بيرجع `{ twoFactorRequired, challengeToken, expiresAtUtc }` بدل الجلسة.
2. `POST /auth/login/two-factor` بياخد `{ challengeToken, code | recoveryCode }` ويرجّع الجلسة.

قواعد الخطوة التانية:
- **الـ challenge** توكن السيرفر بيوقّعه وصلاحيته 5 دقايق، فمش بيتخزّن حاجة في القاعدة للدخول اللي لسه ماكملش. التوكن مربوط بوقت آخر تغيير لكلمة المرور، فلو الباسورد اتغيّر في النص التوكن بيبطل.
- **الكود بيتقبل مرة واحدة.** السيرفر بيحفظ آخر خطوة زمنية اتقبلت (`TwoFactorLastStep`)، فنفس الكود مايتعادش. ومسموح بفرق خطوة واحدة قبل أو بعد، عشان ساعة الموبايل ممكن تبقى متأخرة أو متقدمة شوية.
- **تخمين الكود زي تخمين الباسورد:** كل كود غلط بيتحسب في محاولات الدخول، وبعد 5 الحساب بيتقفل (`MaxFailedLoginAttempts`). عدّاد المحاولات مابيتصفّرش إلا لما الكود ينجح. كل محاولة بتتسجّل في محاولات الدخول بسبب `WrongTwoFactorCode`.
- **الدخول بكود استرداد** بيتعلّم في محاولات الدخول وفي سجل المراجعة.

## إعدادات المستخدم نفسه (`/two-factor`، من رابط في الشريط الجانبي تحت "تغيير كلمة المرور")
| Endpoint | الوظيفة |
|---|---|
| `GET /auth/two-factor` | الحالة، وعدد أكواد الاسترداد الباقية |
| `POST /auth/two-factor/setup` | مفتاح سري جديد (معلّق لحد التأكيد) + رابط `otpauth://` للـ QR |
| `POST /auth/two-factor/enable {code}` | تأكيد بكود من التطبيق، بيشغّل التحقق ويرجّع أكواد الاسترداد |
| `POST /auth/two-factor/recovery-codes {code}` | أكواد جديدة، والقديمة بتبطل |
| `POST /auth/two-factor/disable {password, code \| recoveryCode}` | إيقاف: محتاج **كلمة المرور + كود**، يعني جلسة مسروقة لوحدها ماتقدرش تقفله |

الشاشة فيها:
- QR والمفتاح مكتوب للإدخال اليدوي.
- أكواد الاسترداد، وتقدر تحفظها كملف أو تنسخها. زرار "حفظتها" مابيتفعّلش غير بعد الحفظ أو النسخ.
- تنبيه لما يفضل 3 أكواد أو أقل.

## المدير
- `POST /settings/users/{id}/reset-two-factor` بصلاحية تعديل شاشة المستخدمين. بيمسح المفتاح والأكواد، والمستخدم يدخل بالباسورد لحد ما يشغّله تاني.
- في شاشة المستخدم ظاهر حالة التحقق وزرار "إلغاء التحقق بخطوتين" بتأكيد، و`twoFactorEnabled` بقى موجود في قائمة المستخدمين وتفاصيل المستخدم.

## التخزين والأمان
- **القاعدة:**
  - `Users` اتضاف لها `TwoFactorSecret` و`TwoFactorPendingSecret`، الاتنين **مشفّرين** بـ ASP.NET Data Protection.
  - واتضاف `TwoFactorLastStep`.
  - وجدول جديد `UserRecoveryCodes` فيه `UserId` و`CodeHash` و`UsedAtUtc`.
- **سجل المراجعة:**
  - تشغيل التحقق وإيقافه بيتسجّل تلقائيًا (تغيير `TwoFactorEnabled`).
  - المفتاح بيتسجّل `[REDACTED]` دايمًا، و`TwoFactorLastStep` مابيتسجّلش.
  - جدول أكواد الاسترداد مش متسجّل، زي الـ refresh tokens.
- **مفاتيح التشفير** محفوظة في `App_Data/DataProtection-Keys` جوه فولدر الـ API. المسار ممكن يتغيّر من الإعداد `DataProtection:KeysPath`، وعلى Windows المفاتيح متقفلة كمان بـ DPAPI على مستوى الجهاز.
  - ⚠️ **الفولدر ده لازم يتاخد في الـ backup ويتنقل مع أي نشر.** لو المفاتيح ضاعت، كل اللي مشغّلين التحقق مش هيعرفوا يدخلوا لحد ما المدير يلغيه لهم.
  - لو فيه أكتر من سيرفر، لازم يشاوروا على نفس الفولدر.

## الواجهة
- **شاشة الدخول:** بعد الباسورد بتطلب كود التحقق، وفيها اختيار "استخدم كود استرداد" و"رجوع لكلمة المرور". لو انتهت مهلة الكود أو الحساب اتقفل، بترجع لخطوة الباسورد.
- **الـ QR** بيترسم بمكتبة `qrcode` (npm، 1.5.4)، وأضفت كمان `@types/qrcode`.
